# Research Findings

## Q1: How does the Checklist model and its versioned codec define, decode, and default fields — and how do the store and merge handle missing fields, newer payloads, and keys?

### Findings
- **Model field lists** (`CheckStitchCore/Sources/CheckStitchCore/Checklist.swift:8-19, 52-65, 108-119, 124-128`):
  - `ChecklistItem`: `id: UUID`, `title: String` (required), `modifiedAt: Date`, `revision: Int`.
  - `Checklist`: `id: UUID`, `name: String`, `items: [ChecklistItem]`, `modifiedAt: Date`, `revision: Int`.
  - `ChecklistTombstone`: `checklistID`, `itemID: UUID?` (`nil` = whole-checklist delete), `deletedAt`, `revision`.
  - `ChecklistEnvelope`: `version: Int`, `deviceID: String`, `checklists: [Checklist]`, `tombstones: [ChecklistTombstone]`.
- **Decode defaults** (`Checklist.swift:31-34, 71-75, 145-148`): only sync fields fall back via `??` — item `modifiedAt → .distantPast`, `revision → 0`; checklist `items → []`, `modifiedAt`, `revision`; envelope `deviceID → ""`, `checklists → []`, `tombstones → []`. `id`/`name`/`title`/`version` are hard `decode` — a missing one throws (`Checklist.swift:207`). **A missing optional/sync field never fails decode.**
- **Versioning & classify** (`Checklist.swift:169, 176-209`): `currentVersion = 2`. `classify()` probes `version` first (`Checklist.swift:196, 222`): `loaded(envelope)` for current, `migratable(from: 1, checklists:)` for v1 (drops tombstones/deviceID), `unsupportedVersion` for anything else, `unreadable` on throw.
- **Store load outcomes** (`CheckStitch/ChecklistStore.swift:61-79`): `.loaded` → adopt + `canOverwriteStoredPayload = true`; `.migratable` → `{ migrated(at: now()) }` ("never stall migration", `:67-69`); `.unsupportedVersion` → empty + **read-only** guard (`:70-72`, `save`/`apply` refuse at `:241-244, 195`); `.unreadable` → empty, overwrite allowed (`:73-75`).
- **Envelope is the only encoded shape** (`ChecklistStore.swift:85-90`): always written as `version: currentVersion`. `save()` cancels pending text saves first (`:236-248`).
- **Mutations vs revision bookkeeping** (`ChecklistStore.swift:107-207`): `create` bumps `revision: 1`; `rename`/`updateItem` bump item/checklist revision + `modifiedAt` then `scheduleSave()`; `addItem`/`removeItems`/`delete` call `save()` directly (structural edits bypass the 300 ms coalescing at `:45, 222-235`).
- **Storage keys are fixed** (`ChecklistStore.swift:44, 96`; `CheckStitchCore/Sources/CheckStitchCore/ChecklistSyncing.swift:23, 28-29`): `"checklists.v1"` and `"checklist.deviceID"`; no key-renaming migration exists anywhere.
- **Merge** (`CheckStitch/ChecklistMerge.swift:12-62`): unions tombstones by `(checklistID, itemID)` keeping the higher revision/newer date winner (`:116`); checklist level winner only overwrites `name`/`revision`/`modifiedAt` (`:73-82`); items merge per-id (`:95-113`); tombstones always suppress live entries.
- **Pattern**: a new persisted field means (a) a hard or `??`-defaulted decode for older payloads, (b) an encode that writes it unconditionally, (c) no version bump is forced — but `version > working` payloads are treated as read-only by design (`ChecklistStore.swift:70-72`).

## Q2: What Reminders list/calendar enumeration surface exists (CheckStitch + SingleThread), and how are identifiers represented and used?

### Findings
- **CheckStitch has no enumeration surface.** The entire EventKit footprint is two files: `CheckStitch/ChecklistReminders.swift` and `CheckStitchCore/Sources/CheckStitchCore/ReminderCreating.swift`.
  - `ChecklistReminders.create(from:)` (`CheckStitch/ChecklistReminders.swift:10-28`): fresh `EKEventStore()` per call (`:13`), `requestFullAccessToReminders()` (`:14`), per-item `EKReminder` + `reminder.calendar = eventStore.defaultCalendarForNewReminders()` (`:21`) + `save(reminder, commit: true)` (`:22`). `defaultCalendarForNewReminders()` is the **only calendar-identification API**; the returned `EKCalendar` is never inspected, stored, or compared.
  - `ReminderCreating` protocol (`ReminderCreating.swift:14-17`): just `requestAccess() -> Bool` and `create(title: String)` — **no calendar/list parameter on the seam**. `EventKitReminderCreator` (`:28-52`) wraps one long-lived injected `EKEventStore`; `#if !os(watchOS)` compiles out the save (`:34-37`).
  - Grep across CheckStitch: no `EKCalendar`, `calendars(for:)`, `EKEntityType`, or calendar UUID/name handling anywhere.
- **SingleThread does have enumeration**: `SingleThreadCore/Sources/SingleThreadCore/EventKitStoring.swift:12` — `calendars(for entityType: EKEntityType) -> [EKCalendar]` (returns `EKCalendar` **objects**, not ids/names); `:16-19` — a fetch predicate narrowed by `calendars: [EKCalendar]?`. Consumed only at `ReminderStore.swift:494`: `availableLists = Set(eventStore.calendars(for: .reminder).map(\.title).filter { !$0.isEmpty }).sorted()` — **identity is reduced to the calendar `title` String** for an exclude-list; persisted `setExcludedListTitles` at `:500-505`.
- **Creation targeting in both repos is hard-wired to the system default** (`EventKitStoring.swift:63`, `ChecklistReminders.swift:21`, `ReminderCreating.swift:32`): nothing addresses a specific calendar/list at creation time; no calendar/reminder UUIDs are used anywhere (test corroboration: `SingleThreadTests/ReminderStoreTests.swift:1247, 1267` builds `EKCalendar(for: .reminder, eventStore:)` and asserts `reminder.calendar == eventStore.defaultCalendarForNewReminders()`; `SingleThreadTests/TestFixtures.swift:31, 39-40`).
- **Implication**: enumerating lists exists in the SDK surface via `EKEventStore.calendars(for: .reminder)` (used by SingleThread on this toolchain), but the only identifier pattern observed is calendar title Strings; there is no evidence of a stable (UUID-like) list identifier in either codebase, and the "inbox" is currently reachable only through `defaultCalendarForNewReminders()`.

## Q3: How does the existing reminder-creation flow deal with all-or-nothing concerns, and how are failures surfaced in the UI?

### Findings
- **Two parallel creation paths exist:**
  - **Path A (production)** — `CheckStitch/ContentView.swift:303-319` → `CheckStitch/ChecklistReminders.swift:10-28`, returns `Void`.
  - **Path B (core package, test-only)** — `ChecklistCreator`/`ReminderCreating`/`ChecklistViewModel` (`CheckStitchCore/Sources/CheckStitchCore/`). No production code constructs `EventKitReminderCreator` or `AppEnvironment` (grep: only `ChecklistViewModelTests.swift:7-8`).
- **Path A trace** (`ContentView.swift:303-319`): double-tap guard + lookup (`:306`), `creating.insert(id)` (`:307`), `Task` with min 1 s spinner (`:311`), `await ChecklistReminders.create(from: checklist)` (`:312`), then **unconditionally** `creating.remove(id); created.insert(id)` (`:313-317`). Inside `ChecklistReminders.create`: permission denied → **silent bare `return`** (`:14-15`); per-item `try save` with exceptions caught by a `do/catch` that only `logger.error`s (`:13, 25-27`); blank titles skipped (`:18-19`). No return value — the caller cannot distinguish success/denial/failure. **The green checkmark flashes even on complete failure.**
- **Path B outcome types** (`ChecklistCreator.swift:5-11`): `ChecklistCreationOutcome` = `created(count:)` / `permissionDenied` / `failed(String)` — only `.failed` carries text. `create(from:)` (`:21-33`): access gate → `.permissionDenied` (`:23`); loop over `!isBlank` items, `created += 1` per success (`:25-28`); any throw → `.failed(error.localizedDescription)` (`:29-31`). Partial failure (save throws at item n) unwinds the whole call; items 0..n-1 stay created and the count is lost.
- **ViewModel surfacing** (`ChecklistViewModel.swift:28-44`): `.created` → `isChecklistCreated = true` (`:37-38`); `.permissionDenied` → `break` with no message (`:39-40`); `.failed(message)` → **logged only, never displayed** (`:41-43`). The view model is consumed by no production view today.
- **UI error surfaces that exist**: the only `.alert` in the app is the rename-conflict alert (`CheckStitch/ChecklistDetailView.swift:78-84`); `SyncStatusView` (`ContentView.swift:366-395`) is a sync-status footer fed by `syncService.lastOutcome` (`SyncOutcome`, `CheckStitch/ChecklistSyncService.swift:5-9`), unrelated to reminder creation. There is no per-row failure state, no failed-set, no error text for creation.
- **All-or-nothing today**: none. Per-item commits with `commit: true` (`ChecklistReminders.swift:21`, `ReminderCreating.swift:35`) mean a mid-loop failure leaves a partial set of reminders; no existence check of any destination list precedes creation.

## Q4: How does the edit-checklist screen bind draft state to the store and persist edits; what control/binding patterns exist across the SwiftUI screens?

### Findings
- **Detail screen anatomy** (`CheckStitch/ChecklistDetailView.swift:9-19, 21-89`): keyed by `checklistID: UUID`; reads `ChecklistStore` via `@Environment(ChecklistStore.self)` (`:11`); `if let checklist = store.checklist(id:)` gate with `ContentUnavailableView("Checklist not found")` fallback (`:87-89`). Body: `Form` → `Section("Checklist name")` `TextField("Name", text: $draftName)` (`:22-25`); `Section("Items")` `ForEach(checklist.items)` with per-item `TextField` bound via `titleBinding` (`:27-33`); third section with "Add Item" (`.checkStitchButton()`) and destructive "Remove Checklist" (`:35-54`); toolbar `ToolbarItem(placement: .confirmationAction)` with "Done" → `commitRename()` (`:57-65`).
- **Two binding styles**:
  - Name: **buffered** `@State draftName`, seeded once in `.onAppear` via `didLoadDraft` guard (`:66-70`); committed by `store.rename` only on Done (`commitRename` `:91-96`) or on leaving (`commitDraftIfChanged` `:98-103`); `.nameTaken` → alert (`:78-84`), otherwise conflict dropped silently on disappear (`:71-76`).
  - Items: **per-keystroke** via a custom `Binding<String>` (`titleBinding` `:105-112`) whose getter resolves from the store each read and whose setter calls `store.updateItem` directly; writes coalesce via `scheduleSave()` (`ChecklistStore.swift:222-235`).
- **Store commit machinery** (`ChecklistStore.swift`): `rename` (`:120-130` — `notFound`/`nameTaken` outcomes, case/whitespace-insensitive duplicate check), `updateItem` (`:160-168`), structural edits call `save()` directly; `flushPendingSave()` (`:213-218`) is invoked from the detail screen's `onDisappear` (`ChecklistDetailView.swift:75`) and from `MyApp.swift:51-56, 77-82` on `scenePhase != .active`.
- **Control inventory (app target)** (`CheckStitch/`): `TextField`, `Form`, `Section`, `ForEach`, `NavigationLink` (value-based `ContentView.swift:252`, destination-based `SettingsView.swift:32`), `Button`, `ProgressView`, `ToolbarItem`, `ContentUnavailableView`, `Toggle`/`Link` (`BackgroundSettingsView.swift:11, 36, 71`), and — notably — **`Picker` in both settings screens**: `SettingsView.swift:17` (`appearancePicker`, `.tag(mode)` rows) and `BackgroundSettingsView.swift:23`. Shared button chrome `.checkStitchButton()` = `.buttonStyle(.borderless)` (`CheckStitchButtonModifier.swift:13-25`). **No** `Menu`/`MenuButton`/`.pickerStyle(.menu)` anywhere.
- **Watch target** (`CheckStitchWatch/`): `List`, destination-based `NavigationLink`, `Button` ("Create reminders"/"Sent" toggle at `WatchChecklistDetailView.swift:20`), `Text`; no `TextField`/`Form`/`ToolbarItem`/`Picker`/`Menu`, no alerts.
- **Pattern for a new persisted choice**: settings screens already demonstrate `Picker` with `.tag(...)` rows feeding a binding (SettingsView), while the detail screen demonstrates the buffered-`@State` + commit-on-exit + alert-on-conflict pattern for validated edits.

## Cross-Cutting Observations
- **Right-now creation is in the app target, not the core seam**: production uses `ChecklistReminders.create` (returns `Void`, log-only errors), while the richer `ChecklistCreator`/`ChecklistCreationOutcome`/`ChecklistViewModel` (which already models `failed(String)`/permissionDenied/`created(count)`) has no production consumer. Any error surfaced at run time must connect to `ContentView.createReminders(for id:)` (`ContentView.swift:303-312`), which today shows success unconditionally.
- **The codec is the single source of serialization truth**: `ChecklistStore` is explicitly "the only encoder" (`ChecklistStore.swift:85`), writes `version: currentVersion` envelopes under `"checklists.v1"`, and shares the key with the KVS sync layer (`ChecklistSyncing.swift:23, 28-29`). A new persisted field flows: model `Checklist` → struct decode defaults (hard vs `??`) → encode → classify version struts — with the `.unsupportedVersion` read-only guard protecting newer payloads after any version bump.
- **No stable list identifier exists in either codebase**: enumeration returns opaque `EKCalendar` objects; the only identifier ever persisted is the calendar `title` String (SingleThread `ReminderStore.swift:494-505`). Whether an `EKCalendar` instance/identity survives renames/restarts is not established anywhere in these repos.
- **The settings screens are the existing selection-control precedent**: `Picker` with `.tag(...)` rows appears exactly twice (`SettingsView.swift:17`, `BackgroundSettingsView.swift:23`), both bound through staged bindings written back (ContentView `SettingsBindings`/`writeBack`, `ContentView.swift:361-369`).
- **Two-store split**: the watch target has its own `WatchChecklistStore` (tested against `FakeChecklistSyncTransport` in `WatchChecklistStoreTests.swift`), while iOS/macOS use `ChecklistStore`; WatchChecklistStore tests run on the macOS host. A model field shared via CheckStitchCore could affect both stores.

## Open Areas
- **Calendar identity/lifecycle**: none of the research confirms how the inbox or other Reminders lists are identified across restarts, renames, or permission changes (`EKCalendar` object identity vs title vs any stable id). SingleThread treats titles as identity only for exclusion purposes.
- **Enumeration availability on this toolchain**: the `calendars(for: .reminder)` API is exercised only in SingleThread's codebase (compiled against the same SDK family); no CheckStitch code calls it, so behaviors like `requestFullAccessToReminders()` gating enumeration results or an empty enumeration are unverified here.
- **Atomicity**: nothing in either codebase shows a multi-reminder transactional create; the only validation-before-create pattern (SingleThread `ReminderStore.swift:539` gating on `requestFullAccessToReminders`) is access-level, not existence-level.
- **Merge semantics for a new checklist-level field**: `ChecklistMerge` winners currently overwrite only `name`/`revision`/`modifiedAt` (`ChecklistMerge.swift:73-82`); how a destination-choice would resolve between devices (winner-takes-all vs kept-on-change) has no existing precedent beyond `name`.
