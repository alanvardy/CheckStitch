# Research Findings

## Q1: Watch-side send path — how the button reaches the WCSession

### Findings
- `CheckStitchWatch/WatchChecklistDetailView.swift:8` — `@State private var sent = false`; `:20-28` bottom `Button` labelled "Sent" when `sent` else "Create reminders"; action `sent = store.run(checklist)` (`:24`); `.disabled(sent || visibleItems.isEmpty)` (`:25`).
- `WatchChecklistStore.run(_:) -> Bool` — `CheckStitchCore/Sources/CheckStitchCore/ChecklistSync.swift:87-91`: `guard transport.sendUserInfo(.runChecklist(checklist.id)) else { return false }`; on acceptance sets `pendingRunID = checklist.id` and returns `true`. Doc comment `:80-81`: "`false` means nothing was sent and the UI must not report success".
- `pendingRunID` (`ChecklistSync.swift:70-71`) is **never read by production code** — only by tests (`WatchChecklistStoreTests.swift:62,94`); no retry/resubmission of a dropped or failed run exists.
- `WatchSyncAdapter.sendUserInfo` — `CheckStitchWatch/WatchSyncAdapter.swift:27-31`: `guard session.activationState == .activated else { return false }` (`:28`), then `session.transferUserInfo(message.userInfo)` (`:29`) with the result **discarded**, unconditional `return true` (`:30`).
- `activate()` (`:14-17`): `guard WCSession.isSupported() else { return }`, then `session.delegate = self; session.activate()` — activation is async; if unsupported, activation never completes and every send returns false forever (unexposed).
- Delegate (`:37-50`): only `activationDidCompleteWith` (`:37-45`; reads `session.receivedApplicationContext` for cold launch, then fires `onMessage`/`onActivated`; the `error:` param is ignored) and `didReceiveApplicationContext` (`:47-50`). **No `didFinish` delivery callback** — after `transferUserInfo` returns, the watch has zero observation of delivery/failure.
- `sendUserInfo` returns false **only** when `activationState != .activated` (pre-activation/async-activation in flight, or post-deactivation) — `ChecklistSync.swift:54-57` documents "a send issued in the same turn is dropped".
- Message encoding: `.runChecklist(id)` → `[.runChecklist: id.uuidString]` (`ChecklistSync.swift:24-25,34-36`); decode `init?(userInfo:)` `:19-31`.
- Activation triggers: `WatchChecklistListView.swift:30-31` `.task { store.start(); store.requestRefresh() }` — the `requestRefresh()` in the `.task` races async activation and is dropped; the reliable refresh comes from `onActivated` → `requestRefresh()` (`ChecklistSync.swift:82-87`).
- "Sent" means only "WCSession accepted the transfer", per design notes (`.pi/orksorksorks/.../var-951/plan.md:929`, `structure.md:114`).

## Q2: Phone-side reception — how the phone receives userInfo

### Findings
- `PhoneSyncAdapter.swift:61-76` — `nonisolated func session(_:didReceiveUserInfo:)` (`:70`): `guard let message = ChecklistSyncMessage(userInfo: userInfo) else { return }` (`:71`), then `Task { @MainActor [weak self] in self?.onMessage?(message) }` (`:72`). `didReceiveApplicationContext` (`:76`) funnels to the same `onMessage`.
- Message decode — `ChecklistSync.swift:19-31`: only `context` (Data), `runChecklist` (String parsing as `UUID(uuidString:)`), `requestChecklists` (Bool == true); anything else → `nil`, silently dropped at the `PhoneSyncAdapter.swift:71` guard.
- Activation (`PhoneSyncAdapter.swift:26-33,47-59`): `activate()` guards `WCSession.isSupported()` (`:28`), sets delegate (`:29`), `session.activate()` (`:30`); `activationDidCompleteWith` fires `onActivated` only when state is `.activated` (`:50-51`); `sessionDidDeactivate` re-activates (`:57-59`).
- Wiring (`CheckStitch/MyApp.swift:58-69`): coordinator is created **lazily inside a `.task`** (`:63-66`) with `transport: PhoneSyncAdapter()`, `snapshot: { store.checklists }`, `createReminders: { await ChecklistReminders.create(from: $0) }`, then `coordinator.start()` (`:67`). `start()` installs `transport.onMessage = { [weak self] in self?.handle($0) }` **before** `transport.activate()` (`ChecklistSyncCoordinator.swift:33-40`).
- **No launch-time session wiring**: `AppDelegate.swift` only handles `applicationDidBecomeActive` for appearance (`AppDelegate.swift:24-26`); no `didFinishLaunchingWithOptions`, no WCSession setup before SwiftUI. The receive path exists only after the SwiftUI `.task` runs.
- Delivery/lifecycle facts: queued `transferUserInfo` is delivered by the OS on next launch once a session exists; a delivered message reaches `onMessage` only if it arrives after `coordinator.start()` assigned it. On cold launch the receive path (delegate + `onMessage`) is installed in the same turn as async `session.activate()`, so the async-activation drop window documented for sends (`ChecklistSync.swift:83-85`, `ChecklistSyncCoordinator.swift:31-32`) also applies inbound.
- Guards that drop a message before the coordinator (5): decode failure (`ChecklistSync.swift:19-31` + `PhoneSyncAdapter.swift:71`); `self` nil in weak capture (`:72`); `onMessage` nil pre-`start()` (`ChecklistSyncCoordinator.swift:34`) — no buffering/retry; `isSupported()` false (`PhoneSyncAdapter.swift:28`); coordinator snapshot-ID guard (`ChecklistSyncCoordinator.swift:45-46`).
- There is no queued-retry and no ack/feedback back to the watch; `onMessage` delivery is best-effort single-shot.

## Q3: Coordinator handling and error visibility

### Findings
- `ChecklistSyncCoordinator.swift:26-31` — `start()` sets `onMessage → handle`, `onActivated → pushContext()`, then `activate()` + an immediate `pushContext()`.
- `.runChecklist` handling (`:38-48`): the `guard let checklist = snapshot().first(where: { $0.id == id }) else { return }` at `:40` is a **silent drop** — no log, no reply to the watch, no state. Snapshot wired as `{ store.checklists }` (`MyApp.swift:64-67`).
- Serialized run queue (`:42-47,57`): `pendingRun: Task<Void, Never>`; `let previous = pendingRun; pendingRun = Task { await previous?.value; await createReminders(checklist) }` — chains runs serially as the documented EKCADErrorDomain 1021 workaround (`:41`). `Task<Void, Never>` cannot carry an error and the closure is `(Checklist) async -> Void` (`:10`), so nothing can propagate out.
- Error observation: production `createReminders` closure `MyApp.swift:67` → `ChecklistReminders.create(from:)` returns `ReminderRunOutcome` (`.permissionDenied`/`.destinationMissing`/`.failed`/`.created(count:)`, `ChecklistReminders.swift:15-35`); the closure returns `Void`, so **every outcome is discarded**. `.failed` is only visible via `logger.error` (`ChecklistReminders.swift:27`); `.permissionDenied` and `.destinationMissing` are not even logged.
- Phone→watch feedback: the coordinator only ever calls `transport.sendContext` in `pushContext()` (`:33-35`); `PhoneSyncAdapter.sendUserInfo` (`PhoneSyncAdapter.swift:39-43`) has **zero call sites**. The watch's `receive` handles only `.context`; `.runChecklist`/`.requestChecklists` are `break` (`ChecklistSync.swift:106-116`). No success/failure channel exists back to the watch.
- Other swallow paths: `pushContext()` `try? ChecklistCodec.encode` failure silently dropped (`ChecklistSyncCoordinator.swift:33`); `sendContext` Bool discarded (`:34`, phone logs send failure only `PhoneSyncAdapter.swift:27-37`); phone `activationDidCompleteWith` drops unless `.activated` (`:53-56`).
- Watch feedback is purely local: "Sent" flips on `store.run` acceptance (`WatchChecklistDetailView.swift:24,27,31-33`); `pendingRunID` is never cleared or observed by any delivery callback.

## Q4: Checklist data provenance — where watch IDs come from

### Findings
- Watch list comes **solely** from `WatchChecklistStore.checklists` (`ChecklistSync.swift:70`), filled only in `receive(_:)` from `.context` messages decoded via `ChecklistCodec.classify` (`.loaded` and `.migratable(from >= 2)`); `.runChecklist`/`.requestChecklists` are `break` (`:99-115`). IDs are `Checklist.id: UUID` (`Checklist.swift:143`), carried as `uuidString` (`ChecklistSync.swift:24-25`).
- Context arrives on the watch two ways: `activationDidCompleteWith` reads `session.receivedApplicationContext` then fires `onActivated` → `requestRefresh()` (`WatchSyncAdapter.swift:37-47`); and `didReceiveApplicationContext` (`:48-53`).
- Phone snapshot (`store.checklists`) is populated from App Group `UserDefaults` key `"checklists.v1"` at store `init` (`ChecklistStore.swift:49-97,114`) and from iCloud KVS: `ChecklistSyncService.start()` wires `didChangeExternally` → `reconcile()` and `store.onChange` → `schedulePush()` (500 ms debounce) (`ChecklistSyncService.swift:44-51`); `syncOnLaunch()` nudges `sync.synchronize()` then `reconcile()` (`:55-60`); `pushNow()` at scene background (`:69-77`, `MyApp.swift:81-85`); `reconcileNow()` reads KVS, `apply`s, writes back (`:99-151`).
- `pushContext()` encodes `ChecklistEnvelope(version:currentVersion, deviceID: "", checklists: snapshot())` (`ChecklistSyncCoordinator.swift:31`, `Checklist.swift:290-297`) and sends via `updateApplicationContext` (`PhoneSyncAdapter.swift:27-34`). Pushed on `store.checklists` change (`.onChange` `MyApp.swift:72-76`), `start()`, `onActivated`, and every `requestChecklists` (`ChecklistSyncCoordinator.swift:37-38`).
- **The watch can hold an ID the phone snapshot lacks** — windows: (1) deliberate silent drop at `ChecklistSyncCoordinator.swift:39-41`; (2) stale context — `updateApplicationContext` is latest-state-wins (`ChecklistSync.swift:14`), the phone re-pushes only on observable change or request, so a phone-side delete/edit after the last push leaves the watch listing old IDs until a later push; (3) two-stage activation — the `start()` push is dropped pre-activation, so before the `onActivated` re-push lands the watch shows what was cached in `receivedApplicationContext`; (4) KVS drift — `store.checklists` also mutates via KVS `didChangeExternally` reconcile (`ChecklistSyncService.swift:44-48`) and push to the watch is not coordinated with it; (5) tombstoned/recreated checklists get fresh UUIDs (`ChecklistStore.swift:382-398`, tombstones `Checklist.swift:268-283`) but context pushes omit tombstones, so the watch holds a deleted ID until a later push.

## Q5: Reminder creation on the phone

### Findings
- Two entry paths: in-app button (`ContentView.swift:347-349,373`; guard `:374-376`; spinner Task `:380-383`) and watch-initiated (`MyApp.swift:67` closure → coordinator `handle` `ChecklistSyncCoordinator.swift:39-47`).
- `ChecklistReminders.create(from:)` → `create(from:targeting:)` with `EventKitReminderDestination.shared` (`ChecklistReminders.swift:12-14`): `:15-16` permission via `requestFullAccessToReminders` (false → `.permissionDenied`); `:17` `reminderLists()`; `:18-21` all-or-nothing destination resolution (unresolved → `.destinationMissing`, zero creates); `:22-35` per non-blank item creates returning `.created(count:)`; `:37-39` single `do/catch` → `logger.error` + `.failed` (mid-loop throw leaves a partial set).
- Destination: `ReminderListsSnapshot.resolve` (`ReminderDestinationTargeting.swift:42-49`) — nil identifier → `defaultIdentifier` (`:28` in `EventKitReminderDestination.swift`), matching id otherwise; `defaultCalendarForNewReminders()` used only for its identifier (`:28`).
- `EventKitReminderDestination.create` (`EventKitReminderDestination.swift:32-45`): re-resolves calendar by identifier (guard `else { throw ReminderDestinationError.listMissing }` `:36-38`, TOCTOU mid-loop), builds `EKReminder`, sets title/notes/calendar/dueDateComponents; `#if !os(watchOS) try eventStore.save(reminder, commit: true) #endif` (`:41-43`). `ReminderDestinationError.listMissing` `:53-56` ("some reminders may not have been created").
- `EventKitReminderCreator` (`ReminderCreating.swift:21-40`) is the Core peer seam with **no production consumer** — referenced only in tests; the phone ships `EventKitReminderDestination`. Doc `:12-15`: EKReminder holds a weak store ref — one long-lived store must outlive all reminders.
- EKCADErrorDomain 1021 workaround is **serialization, not retry**: `ChecklistSyncCoordinator.swift:40-42` chains runs so overlapping requests never hold two EKEventStores open; `PhoneSyncAdapter.swift:8-9` comment: adapter owns no store, creation stays on the coordinator closure "so the process keeps a single `EKEventStore`" (`EventKitReminderDestination.shared`).
- Zero-reminder failure conditions: pre-task drop (`ContentView.swift:374-376`); `.permissionDenied` (`:15-16`) — zero; `reminderLists()` throws → `.failed` (`:37-39`) — zero; `.destinationMissing` (`:18-21`) — zero; mid-loop throw → partial set; `#if !os(watchOS)` compiles `save` out entirely `(EventKitReminderDestination.swift:41`, `ReminderCreating.swift:36)`.
- Failure surfacing: **only on the in-app path** — alert "Couldn't create reminders" (`ContentView.swift:156-164` bound to `runErrorMessage` `:29`, set `:390-392`). The sync-coordinator path discards the whole outcome; no feedback reaches the watch.

## Cross-Cutting Observations
- **The entire watch->create chain is best-effort with zero end-to-end feedback**: watch "Sent" = transfer accepted; phone drops are silent at every stage (decode, pre-start `onMessage`, snapshot-ID guard, outcome discard); no message travels back to the watch.
- **Two independent silent-drop gates dominate**: (a) any send/receive issued before async WCSession activation completes, documented at `ChecklistSync.swift:54-57,83-85`; (b) the coordinator's snapshot-ID guard `ChecklistSyncCoordinator.swift:40`.
- **Error visibility exists only in-process**: `logger.error` for `.failed` (`ChecklistReminders.swift:27`); permission-denied and destination-missing are invisible even in logs on the watch path.
- **Single-EventKit-store discipline** is enforced by design (`EventKitReminderDestination.shared`; coordinator closure owns creation; `PhoneSyncAdapter.swift:8-9`); the serialized `pendingRun` queue is the 1021 workaround and is untested in the coordinator suite.
- **All sync transport is modeled by fakes** — no test compiles either real adapter, so every real WCSession behavior (activation timing, queued delivery, background wake) is unverified by automation; the device spike is the only way to distinguish the candidate drop points.

## Open Areas
- Which of the candidate drop points actually fires on hardware is **not determinable from the codebase alone** — needs a device spike on a real paired watch/phone (`bash scripts/run-watch.sh`), with instrumentation (os-log/`logger.error`) to observe: watch-side activation state at tap, whether the phone receives `didReceiveUserInfo`, whether `.runChecklist` enters `handle`, snapshot membership of the id, and the `ReminderRunOutcome` (currently discarded).
- Q2 lifecycle claims (queued delivery when the phone is not running, background wake, cold-launch inbound window) derive from code comments and known WCSession semantics, not hardware verification.
- Whether the OS wakes a backgrounded phone app for `transferUserInfo` delivery is OS behavior, out of the repo's control; the code has no background-arrival wake path (no `applicationDidFinishLaunching` session setup).
- `SpyReminderCreator`/`sharedTestEventStore` definitions were expected in TestFixtures.swift and were found there (TestFixtures.swift:25,30).
