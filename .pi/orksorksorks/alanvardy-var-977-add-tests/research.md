# Research Findings

## Q1: How does the checklist-to-reminders creation flow in `CheckStitch/ContentView.swift` work, end to end?

### Findings
- The sole screen is `struct ContentView: View` (`CheckStitch/ContentView.swift:5`) with `@State checklistName = "checklist"` and an `items` array pre-seeded with three `ChecklistItem`s (`:8-12`), plus boolean flags `isShowingEditChecklist`, `isShowingSettings`, `isCreatingChecklist`, `isChecklistCreated` (`:13-16`).
- `@AppStorage("appearanceMode")` binds `var appearanceMode = AppearanceMode.system` (`:18-19`) to `UserDefaults` key `"appearanceMode"` — the same key `AppearanceModePreference.defaultsKey` uses (see Q2).
- `body` is `GeometryReader` → `HStack` whose width uses `ChecklistWidth.maxContentWidth(viewportWidth:)` (`:21-28`), with `.onChange(of: appearanceMode)` dispatching `#if os(iOS)` `AppDelegate.applyAppearance(new)` (`:34-35`) / `#if os(macOS)` `MacAppDelegate.applyAppearance(new)` (`:37-38`). Two `.sheet`s host `EditChecklistView(name: $checklistName, items: $items)` (`:40-42`) and `SettingsView(appearanceMode: $appearanceMode)` (`:43-45`).
- `createChecklistButton` (`:68-97`) runs a `Task` (`:70-82`): sets `isCreatingChecklist = true`, holds the spinner with `async let minimumSpinner: Void = Task.sleep(for: .seconds(1))` (`:73-74`), `await createChecklistReminders()` (`:75`), then flashes `isChecklistCreated` for one second (`:77-80`).
- `createChecklistReminders() async` (`:120-141`) is the persistence flow:
  1. `let eventStore = EKEventStore()` — a fresh real EventKit store per invocation (`:121`; `import EventKit` at `:1`).
  2. `let granted = try await eventStore.requestFullAccessToReminders(); if !granted { return }` (`:123-124`) — silent return on denial.
  3. Per-item loop (`:126`), skipping blank titles via `guard !item.title.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty else { continue }` (`:127`).
  4. `let reminder = EKReminder(eventStore:)` (`:130`), `reminder.title = item.title` (`:131`), `reminder.calendar = eventStore.defaultCalendarForNewReminders()` (`:132`) — the Reminders Inbox calendar.
  5. `try eventStore.save(reminder, commit: true)` (`:133`).
  6. Outer `do {…} catch { Self.logger.error("Failed to create checklist reminders: \(error.localizedDescription, privacy: .public)") }` (`:122, 136-137`).
- **Object inventory:** only `EKEventStore` (one) and `EKReminder` (one per non-blank item) are constructed. No `EKEvent` anywhere in `CheckStitch/` or SingleThread (grep returns nothing) — the access "request" is `requestFullAccessToReminders() -> Bool`.
- **Models:**
  - `enum ChecklistWidth` (`:145-151`): `nonisolated static func maxContentWidth(viewportWidth: CGFloat) -> CGFloat { min(340, viewportWidth * 0.6) }` (`:147-150`). The doc comment (`:145-148`) says `nonisolated` keeps the pure math callable outside the app target's `MainActor` isolation.
  - `struct ChecklistItem: Identifiable` (`:155-158`): `let id = UUID()` (stable identity so duplicate titles aren't conflated) + `var title: String`.
  - `struct EditChecklistView: View` (`:162-223`) mutates the shared `@Binding` arrays: `.onDelete(perform: remove)` with `private func remove(at offsets: IndexSet) { items.remove(atOffsets: offsets) }` (`:220-222`) and `items.append(ChecklistItem(title: "New item"))` (`:188`). No persistence — creation happens only via the main button's task.
- **SwiftUI vs pure-logic split:** SwiftUI types (`@State`/`@Binding`/`@Environment`, `View`, `GeometryReader`, `.sheet`, `Button`, `TextField`) dominate the file; the isolatable, UI-free pieces are `ChecklistWidth.maxContentWidth` (`:147-150`), the `ChecklistItem` data struct (`:155-158`), and the blank-title guard + per-item loop body inside `createChecklistReminders` (`:126-133`).
- **Provenance:** the `requestFullAccessToReminders()` → `save(reminder, commit: true)` → `logger.error(..., privacy: .public)` pattern mirrors `SingleThreadCore/Sources/SingleThreadCore/ReminderStore.swift:254, 263, 350, 355, 537` — the reference implementation `AGENTS.md:45` points to.

## Q2: How does the appearance system in CheckStitch work across platforms?

### Findings
- Code lives in three app files: `AppearanceMode.swift`, `AppDelegate.swift`, with wiring in `ContentView.swift` and `MyApp.swift`.
- `AppearanceMode.swift:1-8` — conditional imports: `Foundation` + `SwiftUI` always; `UIKit` under `#if os(iOS)`; `AppKit` under `#if os(macOS)`.
- `:16-19` — `enum AppearanceMode: String, CaseIterable { case system / light / dark }` (raw values match persisted strings).
- Platform mappings (machine-gated):
  - iOS `:23-33` — `#if os(iOS)` `windowOverrideStyle: UIUserInterfaceStyle`; `.system → .unspecified` (sentinel for "clear override → follow device"), `.light → .light`, `.dark → .dark`.
  - macOS `:35-45` — `#if os(macOS)` `appKitAppearance: NSAppearance?`; `.system → nil`, `.light → NSAppearance(named: .aqua)`, `.dark → NSAppearance(named: .darkAqua)`.
  - Platform-agnostic: `colorScheme: ColorScheme?` (nil/.light/.dark) for SwiftUI previews `:51-57`; `systemImage: String` (SF Symbols) `:60-66`; `title: String` `:69-75`.
- `:80-81` — `static func load(from defaults: UserDefaults = .standard) -> Self` = `Self(rawValue: AppearanceModePreference(defaults: defaults).rawValue) ?? .system`.
- `AppearanceModePreference` struct (`:90-96`), `static let defaultsKey = "appearanceMode"` (`:100-101`) — one shared key for both `@AppStorage` and `load(from:)`. `var rawValue: String` (`:103-110`) reads `defaults.object(forKey: key) as? String`, validates membership in `["system", "light", "dark"]`, else `"system"`. `func setRawValue(_ raw: String)` → `defaults.set(raw, forKey: key)` (`:112-113`).
- `AppDelegate.swift` is two disjoint `#if os(...)` blocks:
  - iOS `final class AppDelegate: NSObject, UIApplicationDelegate` (`:8`); `static func applyAppearance(_ mode: AppearanceMode, to windows: [UIWindow]? = nil)` (`:13`) resolves default windows from `UIApplication.shared.connectedScenes.compactMap { $0 as? UIWindowScene }.flatMap(\.windows)` (`:14-16`) and sets `window.overrideUserInterfaceStyle = mode.windowOverrideStyle` (`:17-20`); `applicationDidBecomeActive` re-applies via `AppearanceMode.load()` (`:23-25`).
  - macOS `final class MacAppDelegate: NSObject, NSApplicationDelegate` (`:37`); `applyAppearance` loops `for window in NSApp.windows { window.appearance = mode.appKitAppearance }` (`:41-44`); `applicationDidFinishLaunching` (`:47-49`) and `applicationDidBecomeActive` (`:51-53`) both apply `AppearanceMode.load()`.
- Registration: `MyApp.swift:11-13` `@UIApplicationDelegateAdaptor(AppDelegate.self)` `#if os(iOS)`; `:15-17` `@NSApplicationDelegateAdaptor(MacAppDelegate.self)` `#if os(macOS)`.
- User path: `SettingsView.swift:6-18` `Picker(selection: $appearanceMode)` over `AppearanceMode.allCases` (`Label(mode.title, systemImage: mode.systemImage).tag(mode)`); previews use `.preferredColorScheme(AppearanceMode.dark.colorScheme)` (`SettingsView.swift:39-46`).
- Data flow: `UserDefaults` raw string (`AppearanceMode.swift:106` read / `:113` write) ⇄ `ContentView.appearanceMode` via `@AppStorage` (`ContentView.swift:18-19`) → user `Picker` → `.onChange` (`ContentView.swift:32-39`) → platform `applyAppearance` (`ContentView.swift:34/37`) → `UIWindow.overrideUserInterfaceStyle` (iOS) / `NSWindow.appearance` (macOS). Delegates independently re-apply on lifecycle events.

## Q4: What concrete patterns do SingleThread's unit test files use with the Swift Testing framework?

### Findings
- Layout: unit tests in `SingleThreadTests/` (80 Swift files) and `SingleThreadWatchTests/` (8 files); `SingleThreadUITests/` is the **only** place importing XCTest (`SingleThreadUITests/SingleThreadUITests.swift`). Every unit file uses `import Testing`; no XCTest in unit targets.
- Imports: `@testable import SingleThread` + `import Testing` (e.g. `SingleThreadTests/CardWidthTests.swift:1-3`); `@testable import SingleThreadCore` (`ReminderStoreTests.swift:2`, `ReminderDictationParserTests.swift:3`); watch tests `import SingleThreadCore`, `@testable import SingleThreadWatch`, `import WatchConnectivity` (`WatchSyncPipelineTests.swift:1-5`).
- Suite containers: `struct`s named `<Thing>Tests` matching file names. Plain struct for pure logic (`CardWidthTests.swift:5`); `@MainActor` on the struct in 54 of 80 files, often paired with `@Suite(.serialized)` — all 30 explicit `@Suite(` uses carry `.serialized` (e.g. `ReminderStoreTests.swift:15`); no bare `@Suite`. Nested `@Suite(.serialized)` blocks exist inside large files (`ReminderStoreTests.swift:569, 806`).
- Test functions: named by behavior as past-tense sentences, **never `test`-prefixed** (`func maxContentWidthScalesBelowCeiling()` `CardWidthTests.swift:7`; `func plainTextReturnsAsTitle()` `ReminderDictationParserTests.swift:12`; `func visibleRemindersFiltersSkippedReminder()` `ReminderStoreTests.swift:22`).
- Parametrized: `@Test(arguments: [...])` with direct value arrays (e.g. `ReminderSkipTests.swift:23, 37, 60, 87, 108` — `[nil, "", "   ", "\n\n", "t", "t "]` at `:108`; watch `ShowCompletionGlowStateTests.swift:45`, `WatchSyncPipelineTests.swift:86`).
- Assertions: `#expect(value == expected)` universal, with optional trailing failure-message argument (`ReminderStoreTests.swift:26`); reference identity `#expect(first === second, ...)` (`WatchAppViewModelTests.swift:20-22`); `try #require(...)` for unwrapping (`WatchSyncPipelineTests.swift:33, 253, 303`; chains in `LocalizationTests.swift:24-50`). No `#expect(throws:)`, no `.tags`.
- Organization: doc-comments per behavior; `// MARK:` sections group tests (`ReminderDictationParserTests.swift:8, 17, 27`). Big suites share one file deliberately because `makeReminder` fixtures are file-scoped (`ReminderStoreTests.swift:5-8`, with `swiftlint:disable file_length`).
- Coverage scale: `ReminderStoreTests` 70 `@Test`, `SkippedReminderSyncServiceTests` 36, `ReminderDictationParserTests` 34, `EventKitStoringTests` 23, `UITestingSeedTests` 20, `SingleThreadTests` 20 (view-render smoke tests, `SingleThreadTests.swift:11-21`), plus many small suites (AppearanceMode, CardWidth, SortOption, …). Watch tests cover viewmodel stability/glow seam, sync pipeline, and completion-glow states.
- Shared fixtures are cross-file free functions at global `@MainActor` scope, imported as top-level symbols (`ReminderStoreTests.swift:23` uses `makeReminder` with no local definition).

## Cross-Cutting Observations
- **The reference repo is the pattern source for both architecture and tests.** CheckStitch's EventKit flow (`ContentView.swift:120-141`) is a smaller copy of SingleThread's `ReminderStore`; CheckStitch's `ChecklistWidth` doc comment (`ContentView.swift:145-148`) explicitly mirrors SingleThread's `CardWidth`. Any test facade/refactor will be judged against that correspondence.
- **Actor isolation is the recurring seam.** App/watch targets set `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`; pure math escapes via `nonisolated` (`ContentView.swift:147-150`); all EventKit test fixture builders are `@MainActor`; fakes use `@unchecked Sendable`; rendezvous helpers are `actor`s.
- **Test discovery is folder-based in both repos** (`PBXFileSystemSynchronizedRootGroup`), so a new test folder auto-syncs without pbxproj edits — same mechanism as app sources.
- **Framework split is strict:** Swift Testing (`@Test`/`@Suite(.serialized)`/`#expect`/`#require`) in unit targets; XCTest only in UI smoke tests. Test functions are behavior-named past-tense, never `test`-prefixed (SwiftFormat `preferSwiftTesting`).
- **Platform matrix:** unit suites run on macOS host (`CODE_SIGNING_ALLOWED=NO`); iOS UI tests run on a prebooted simulator via `build-for-testing` + `test-without-building`; watch suites need their own sim and a local `lib_TestingInterop.dylib` embed. Platform-only fixtures are `#if os(...)`-gated.
- **Destination discipline is enforced everywhere**: `.simulator_id` wins over explicit overrides only for exports; bare `name=` destinations are forbidden as they wedge shared sims.
- **Gate tooling is heavier in SingleThread**: swiftformat + swiftlint `--strict` + periphery `scan --strict` + deployment-target verification run before any test, and result bundles are consumed via `xccov` (coverage) and `xcresulttool` (test-one).
