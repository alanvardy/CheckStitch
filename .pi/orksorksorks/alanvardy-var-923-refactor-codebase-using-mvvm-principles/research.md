# Research Findings

Areas surveyed: the CheckStitch app target (views + platform delegates), the
CheckStitchCore SPM package, CheckStitchTests / CheckStitchUITests, the
CheckStitchWatch target, the build/gate scripts, and the SingleThread mirror
repo's MVVM shape. Here follows what exists and how the layers connect; no
prescription.

## Q1: How does CheckStitch/ContentView.swift hold presentation and domain behaviour, and how does MyApp.swift wire the core universe in?

### Findings
- Single fat view type. `struct ContentView: View` (`CheckStitch/ContentView.swift:6`) mixes SwiftUI presentation (plate styling, navigation stack, overlays, dialogs) with the app's domain-flow logic (mutation calls into core, async reminder creation, import/export orchestration, settings persistence). There is no app-side view model; the two core objects are the de-facto domain layer.
- Environment/state surface: `@Environment store: ChecklistStore` (:7), `syncService: ChecklistSyncService` (:8), `colorScheme` (:9). `@AppStorage` prefs `appearanceMode`, `backgroundEnabled`, `backgroundFadePercent`, `backgroundPinned`, `textSize`, `allowsLandscape` (:11-17). ~25 `@State` fields (:19-46) hold both pure view-transient UI (edit mode, `creating`/`created` spinners, settings-sheet flag) and domain-flow state (`checklistPendingRemoval`, `importSession`, `conflict`, `exportDocument`, `runErrorMessage`, `dataActionQueue`). Domain work-in-progress is owned in the view, not a view model.
- List mutation is done directly against the core store: `createChecklist()` (:494) → `store.create().id` then `path.append(...)`; `createReminders(for id)` (:500) → `ChecklistReminders.create(from: checklist)` inside a `Task`, mapping `.created` → green feedback and `.destinationMissing/.permissionDenied/.partiallyCreated/.failed` → `runErrorMessage`; `removeChecklist(id)` (:528) → `store.removeChecklists(at: IndexSet(integer: index))`; `moveChecklist(id, up)` (:537) → `store.moveChecklists(from:…, to: up ? index-1 : index+2)`.
- Settings bridge: staged `SettingsBindings` bag — `makeSettingsBag()` snapshots current prefs (:583); `settingsSheetWritebacks(bag)` fires `SettingsView` with the bag + live bindings and `writeBack(bag)` (:574) persists staged changes back to `@AppStorage` fields; `AppLanguage` goes through a write-through `appLanguageBinding` → `AppLocaleState.current`. Import/export menu choices are staged in a `SettingsDataActionQueue` (`dataActionQueue.stage(action)`, :594) and `perform()` (:601) opens the panel after the sheet dismisses.
- Import/export flow: `exportSelected()` (:613) filters `store.checklists` by `exportSelection`, builds core `ChecklistExportDocument(checklists: selected)`, sets `exportDocument`/`isExporting`. `importFile(at url)` (:625) reads `Data(contentsOf: url)` under a `startAccessingSecurityScopedResource`/`stopAccessing` pair, hands it to `ChecklistImportSession(store: store).prepare(data:)` (catches `ChecklistImportError`); FIFO conflicts via `conflictPresented` binding, decisions via `importSession?.decide(decision, for: current.id)` and `advancedConflict()`.
- Core calls made from the view: `store.create/createChecklists/checklists/checklist/moveChecklists/removeChecklists/flushPendingSave`, `ChecklistReminders.create`, `ChecklistExportDocument`, `ChecklistImportSession(.prepare/.decide/.pending)`, `ChecklistSyncService.start/refresh/syncOnLaunch/pushNow/sync`, `UbiquitousChecklistSync`, `ChecklistSyncCoordinator(.start/checklistsDidChange/languageDidChange)`, plus `AppLocaleState.current.{language,effectiveLocale}`, `AppearanceMode`, `TextSize`, `BackgroundFade`, `ChecklistWidth`, `SettingsBindings`, and the local `SettingsDataActionQueue` (:687-703). For checklist mutation the domain logic lives in core, but orchestration, side-effect scheduling and error handling live in the view.
- `@main struct MyApp: App` (`CheckStitch/MyApp.swift:10`) owns core singletons as app-level `@State`: `store: ChecklistStore`, `syncService: ChecklistSyncService`, iOS-only `coordinator: ChecklistSyncCoordinator?` (:20-23). `init()` (:27) constructs both and calls `syncService.start()`. `body` builds `WindowGroup { ContentView() }` and injects `.environment(store).environment(syncService)`, plus `.environment(\.locale, AppLocaleState.current.effectiveLocale)` and `.restorationBehavior(.disabled)` on macOS (:32-47).
- iOS-only wiring (:48-65): a `.task` lazily builds/starts `ChecklistSyncCoordinator(transport: PhoneSyncAdapter(), snapshot: { store.checklists }, createReminders: { await ChecklistReminders.create(from: $0) }, language: { AppLocaleState.current.language })`; `.onChange(of: store.checklists)` → `coordinator?.checklistsDidChange()`; `.onChange(of: AppLocaleState.current.language)` → `languageDidChange()`. Both platforms run `.task { await syncService.syncOnLaunch() }` and flush on suspend via `.onChange(of: scenePhase)` → `store.flushPendingSave()` + `syncService.pushNow()` when not `.active` (:38-40, :74-78).

## Q2: What does the CheckStitchCore package contain and how is it structured?

### Findings
- Package definition (`CheckStitchCore/Package.swift:1-20`): local SPM, `swift-tools-version: 6.0`, name `CheckStitchCore`, one library target; platforms `.iOS("18.7")`, `.macOS("27.0")`, `.watchOS("26.0")` (:7-10). Sources-only — a comment (:3-4) states it is tested by the app-hosted `CheckStitchTests` target via `@testable import`, never by `swift test`; no `Tests/` dir. Target has `resources [.process("Resources")]` (:17-19); no module deps on other packages. Source layout: 20 files, 1790 lines under `Sources/CheckStitchCore/`.
- Dependency container: `AppEnvironment.swift:5-14` — `public struct AppEnvironment: Sendable` holding one service `reminderCreator: RemindingCreating`. Named `AppEnvironment` (not `Environment`) to avoid clashing with SwiftUI's exported `Environment<Value>` (doc note :5-8).
- Models: `Checklist.swift:8` `ChecklistItem: Identifiable, Codable, Hashable, Sendable` (row :37-139: `id`, `title`, `description`, `modifiedAt`/`revision`, per-field clocks `titleRevision`/`descriptionRevision`/etc., `relativeDate: Int?` days-only, `priority`). `Checklist.swift:145` `Checklist` (list model); `:307` `ChecklistTombstone`; `:323` `ChecklistEnvelope`; `:367` `ChecklistCodec` (+ `.Outcome` :375) — the sync/codable identity.
- Support models: `ChecklistItemPriority` (`ChecklistItemPriority.swift:6`, raw Int mirroring `EKReminder.priority` 0/9/5/1), `ChecklistItem+DueDate.swift` (20 lines, relative-days→date), `ChecklistTitleNumbering` (`ChecklistCreator.swift:16`), `AppInfo.swift:6`, `AppearanceMode.swift:16` (`AppearanceMode: String, CaseIterable`; `AppearanceModePreference` :92), `AppLanguage.swift:5`, `AppLocaleState.swift:9` (`@MainActor` state class), `SharedStrings.swift:7`, `LocalizedString+Shared.swift`.
- EventKit seams: `ReminderCreating.swift:9-14` `public protocol ReminderCreating: Sendable` with `requestAccess() async throws -> Bool` and `create(title:dueDateComponents:)`; real adapter `EventKitReminderCreator` (:21-44) `@MainActor`, holds one long-lived `EKEventStore`, `#if !os(watchOS)` guards `save` (watchOS EventKit read-only). `ReminderDestinationTargeting.swift:104-111` `@MainActor protocol` with `requestAccess()`, `accessStatus()` (no prompt), `reminderLists()`, `create(title:notes:priority:in:dueDateComponents:)`; supporting types `ReminderListOption` (:5), `ReminderListsSnapshot` (:18, `resolve`/`selectableOptions`/`pickerSelection`), `ReminderRunOutcome` (:58, `errorMessage` map incl. `partiallyCreated`), `ReminderAccessStatus` (:102).
- Sync: `ChecklistSyncing.swift:22` `UbiquitousChecklistSync`; storage/messages in `ChecklistSync.swift` (`ChecklistSyncKey:5`, `RunResultKind:22`, `RunResult:88`, `ChecklistSyncMessage:102`, `PendingRun:214`, `RunPhase:225`, `WatchChecklistStore:249`); diagnostics `SyncGate`/`ChecklistSyncDiagnostics` in `ChecklistSyncDiagnostics.swift:8,30`; `ChecklistSyncCoordinator` (`ChecklistSyncCoordinator.swift:6`) is the phone-side seam wiring transport→reminder creation.
- Checklist creator: `ChecklistCreator.swift:30-65` `public struct ChecklistCreator: Sendable`; `init(reminders:now:calendar:prefixNumbers:)` (:33); `create(from:)` (:41) requests access, drops blanks, number-assigns position after blank drop, one reminder per item, returns `ChecklistCreationOutcome` (`created(count:)`/`permissionDenied`/`failed`, :5-11). This is the seam `ChecklistViewModel` drives.
- Preference/width: `AppLanguagePreference.swift:5-30` persists raw app-language string in `UserDefaults.standard` key `"appLanguage"` (:14), missing/unrecognized → `.system` (:17-22). `ChecklistWidth.swift:9-11` static `maxContentWidth(viewportWidth:)` = `min(340, viewportWidth*0.6)`, `nonisolated` (callable outside app MainActor).
- Partial `ChecklistViewModel.swift:1-57` — the key existing core view model: `@Observable @MainActor public final class ChecklistViewModel` (:8-9). Holds `checklistName = "checklist"` (:17), `items` seeded with 3 defaults "one/two/three" (:18-22), `isCreatingChecklist` and `isChecklistCreated` as `public private(set)` (:24-25). `init(environment: AppEnvironment, spinnerDuration: Duration = .seconds(1))` (:13-16) builds a private `ChecklistCreator` from `environment.reminderCreator`; `spinnerDuration` injectable (tests pass `.zero`). `createChecklist()` (:25-45) sets creating flag, holds spinner ≥ `spinnerDuration` via `async let`, calls `creator.create(from: items)`, maps `.created→isChecklistCreated=true` / `.permissionDenied→break` / `.failed→logger.error`. `dismissCreatedFeedback()` (:48-50). Private `logger`, `creator`, `spinnerDuration` (:52-57).
- Partial by design: covers name/items/creation/spinner/success only; does **not** own destination-list selection, notes, or priority — those live in the app target. The run path (destination targeting) has **no** view model in the package; the targeting types are protocol/seams without an app-side VM in core.
- Not in CheckStitchCore: `SettingsBindings` and `SettingsDataActionQueue` are defined in the app target (`CheckStitch/SettingsBindings.swift`), not the package.

## Q3: What MVVM shapes does the SingleThread mirror use?

### Findings
- Classic MVVM split across `SingleThread/` (app), `SingleThreadCore/` (SPM package) and `SingleThreadWatch/`. View models are `@MainActor @Observable final class`es residing in the **app and watch targets — never in Core**. The Core package holds the model/store layer (`ReminderStore`, `*Store`, `*Preference`, `*State`, EventKit seam). Views are thin: pure display of injected view-model state, delegating every mutation through the view model.
- App composition root: `SingleThread/SingleThreadApp.swift:55` `@State private var viewModel = AppViewModel()`; body builds `ContentView(viewModel: viewModel.makeContentViewModel(openURLAction:), appViewModel: viewModel)` (:17-18); iOS via `@UIApplicationDelegateAdaptor`, macOS via `@NSApplicationDelegateAdaptor`.
- `AppViewModel.swift:17` `@MainActor @Observable final class AppViewModel`: constructs `ReminderStore` from launch args, wires WatchConnectivity sync + Widget reload hooks, produces the root `ContentViewModel` via `makeContentViewModel(openURLAction:)` (:147). Holds `store`, `backgroundImage`, `usesInMemoryStore`, `notificationScheduler`, `syncService`; notification scheduling/annotation under `#if os(iOS)`.
- `ContentViewModel.swift:15` root list VM: holds `store`, `backgroundImage`, child `dictation`, `urlOpener`; presentation state `nudgeIdentifier`, `isRefreshing`, `enableActionButtons`, `showsActionButtons` (~:80), `completionGlow`/`completionMomentum`. Static presentation copy factories `emptyStateCopy(hasHidden:)`/`allDoneStateCopy()` (:102-141). Handler methods forward to the store: `completeCurrentReminder()` (:224), `skipCurrentReminder()` (:245), `deleteCurrentReminder()` (:249), `rescheduleReminder`/`undoLastCompletion`/`reload`/`refreshManual`/`setExcludedListTitles`, lifecycle `task(showUndatedReminders:)` (:155), deep-link `openInReminders`. `ContentView` delegates mutations to it across many call sites (`ContentView.swift:232/279/293/296/325/413/472/483/491/527`).
- `DictationViewModel.swift:10` (child of ContentViewModel): speech → parse → `store.addReminder`; holds `isDictating`, `isProcessing`, `dictationText`, `dictationError`, `creationFeedback`; `startDictation()` (:42).
- `SettingsViewModel.swift:11` thin observable delegating device/widget side effects (`allowsLandscapeChanged` iOS, `showPreferenceChanged` WidgetKit); injected into `SettingsView.swift:24`, `ReminderSettingsView.swift:21`, `InterfaceSettingsView.swift:35`, `ContentView+Settings.swift:15`.
- View visibility: `ContentView.swift:20` takes `ContentViewModel` + optional `AppViewModel`; three init overloads for previews build their own `ContentViewModel`; keeps `@AppStorage` for appearance/textSize (:70-76); `@Environment(\.locale)` and deep-link openURL come from the scene. `ContentView+*.swift` decompose the single screen: `+iOS.swift`, `+Settings.swift`, `+ActionMenu.swift`, `+Previews.swift`.
- Watch: `SingleThreadWatchApp.swift:12` `@main` builds `WatchAppViewModel()` in `init`; `WindowGroup { WatchReminderView(viewModel: viewModel.reminderViewModel) }` (:18-21). `WatchAppViewModel.swift:10` `@MainActor final class` composition root (builds store from launch args `uiTestingStore`, instantiates all `Show*State` holders, `entitlementState`, wires `SkippedReminderSyncService`; lazy `reminderViewModel` (:83)). `WatchReminderViewModel.swift:17` `@MainActor @Observable` root watch-card VM: 8 store/state deps + presentation state (`isRefreshing`, `nudgeIdentifier`, `isShowingNudgeDialog`, `isShowingActionMenu`, `isShowingRescheduleSheet`, `rescheduleDate`, `rescheduleFailure`, `isShowingCompletionTransition`, `transitionReminder`) and handlers `confirmReschedule()`, `task()`, `isNudged`, `completeCurrentReminder()`, `refreshFromCardTap()`, `refresh()`.
- Watch `Show*State.swift` files (`ShowDateState.swift:6` etc.): `@Observable final class` holders replacing `@AppStorage` — `isEnabled` + `apply(_:)` driven by the sync pipeline's `onShow*Received` callbacks; `EntitlementState.swift` same pattern.
- Core (model layer, no view models): `SingleThreadCore/Sources/SingleThreadCore/` holds `ReminderStore.swift` (model aggregate/mutations), EventKit seam `EventKitStoring.swift`/`InMemoryEventStore.swift`, `*Store.swift` types (`CompletionCounterStore`, `SkippedReminderStore`, `ExcludedListStore`, `UndoStore`, `DailyCompletionStore`, `PendingCompletionStore`, `SkipCountStore`, `BoolPreferenceStore`), preference/state types (`AppLanguagePreference`, `AppearanceModePreference`, `AppGroup`, `PreferenceHolder`, `EntitlementState/Store`), sync (`SkippedReminderSyncService`), AppIntents (`ReminderIntents.swift`). No `*ViewModel` type lives in Core.
- App and watch view-model shapes are deliberately mirrored: both `ContentViewModel` and `WatchReminderViewModel` implement the same `task()`/`RecheckerFactory`/`refresh()`/nudge logic and the same `isRefreshing` guard; `AppViewModel.makeContentViewModel` and `WatchAppViewModel.reminderViewModel` are both composition roots injecting the same `ReminderStore`.
- `SingleThreadTests` has dedicated suites per VM (`ContentViewModelTests.swift`, `SettingsViewModelTests.swift`, `ReminderDictationTests.swift`, `CompletionGlowTests.swift`), constructing the VMs directly with fake stores/transcribers.

## Q4: How are the CheckStitch test suites structured?

### Findings
- Build structure: `CheckStitchTests` and `CheckStitchUITests` are sibling `PBXNativeTarget`s in `CheckStitch.xcodeproj/project.pbxproj`. `CheckStitchTests`: `productType = "com.apple.product-type.bundle.unit-test"`, product `CheckStitchTests.xctest`, package dep `CheckStitchCore` (:163-185). `CheckStitchUITests`: `productType = "com.apple.product-type.bundle.ui-testing"`, product `CheckStitchUITests.xctest`, dep `CheckStitchCore` (:187-209). The `CheckStitch.xcscheme` lists both `.xctest` products as `parallelizable=NO` Testables within one TestAction (:49-64).
- CheckStitchTests — 48 Swift files, each file one suite, no aggregator. Two frameworks: Swift Testing (majority) `struct XTests { @Test func … #expect(...) }` (`SmokeTests.swift:6-10`, `ViewRenderTests.swift:7-8`, `ChecklistRemindersTests.swift:7`), many `@MainActor struct` (`ViewRenderTests.swift:6`, `WatchChecklistStoreTests.swift:5`); XCTest (minority) `final class XTests: XCTestCase func test…() throws` (`ChecklistStoreTests.swift:6`, `ChecklistCodecTests.swift:6`, `ChecklistExportTests.swift:6`). `SmokeTests.swift` is a permanent canary (`@testable import CheckStitchCore`). Imports vary: `@testable import CheckStitch` (whole app, e.g. `ViewRenderTests`) or just Core/EventKit/Foundation (`TestFixtures.swift:1-3`, `ChecklistCodecTests.swift:2-3`).
- Coverage scope: fixtures/helpers `TestFixtures.swift`, `BackgroundTestFixtures.swift`, `StubBundle.swift`, `LocalizationFixtures.swift`, `LocalizationTestHelpers.swift`. Core domain: `ChecklistItemTests`, `ChecklistItemDateTests`, `ChecklistCreatorTests`, `ChecklistCodecTests`, `ChecklistMergeTests`, `ChecklistWidthTests`, `ChecklistStoreTests`. Sync: `ChecklistSyncCoordinatorTests`, `ChecklistSyncMessageTests`, `ChecklistSyncServiceTests`, `UbiquitousChecklistSyncTests`, `ReminderListsSnapshotTests`, `WatchChecklistStoreTests`, `ChecklistEntityQueryTests`. Reminders/EventKit: `ChecklistRemindersTests`, `EventKitReminderCreatorTests`, `EventKitReminderDestinationTests`. Settings/preferences: `AppearanceModeTests`, `AppearanceModePreferenceTests`, `OrientationPreferenceTests`, `TextSizeTests`, `SettingsBindingsTests`, `SettingsDataActionQueueTests`, `AppLanguageTests`, `AppLanguagePreferenceTests`, `AppLanguageSyncTests`, `InterfaceSettingsViewTests`, `PrivacySettingsContentTests`, `BackgroundFadeTests`, `BackgroundImageStoreTests`, `BackgroundPhotoLayerTests`. Views/intents: `ViewRenderTests`, `ChecklistDetailViewTests`, `AboutViewTests`, `ExportChecklistsViewTests`, `ListChecklistsIntentTests`, `RunChecklistIntentTests`, `MacWindowFrameTests`, `CardPlateTests`, `ChecklistViewModelTests`, `LocalizationTests`, `LocalizedStringResolutionTests`, `HarnessTests`.
- Platform gating: conditional compilation with `#if os(...)`/`#else` inside test files, no separate per-platform files — `ViewRenderTests.swift:27` `#if os(macOS)` uses `ImageRenderer(...).nsImage`, `#else` `.uiImage` (:27-29); `MacWindowFrameTests.swift:7` nests its struct with macOS-specific indirection.
- CheckStitchUITests — single file `final class CheckStitchUITests: XCTestCase`, XCUIAutomation-based (no Swift Testing). - Coverage: single launch-and-accessibility smoke test — verifies buttons render and runs `performAccessibilityAudit` (:28-38). Platform gating: `#if os(iOS)` restricts the audit to `[.sufficientElementDescription, .trait]` categories; `#else` (macOS) calls `performAccessibilityAudit()` with no categories (:31-37), because macOS's `XCUIAccessibilityAuditType` category set differs. Comment: cheap non-rendering categories only — `.dynamicType`/`.hitRegion` can hang virtualized runners and are covered by unit suites instead.
- Limits: `#if os` gating spans the tree but the grep was sampled (40-match cap); the macOS vs iOS test-phase split is confirmed by the UI-test comments and the scheme's shared config, but actual per-phase run config lives outside these two files.

## Q5: How is the CheckStitchWatch watchOS target structured?

### Findings
- Target layout (`CheckStitchWatch/`): four Swift files — `CheckStitchWatchApp.swift` (app entry), `WatchChecklistListView.swift` (list), `WatchChecklistDetailView.swift` (detail), `WatchSyncAdapter.swift` (WCSession transport) — plus `Localizable.xcstrings` and `{de,en,es,fr,ja,zh-Hans}.lproj/` (watch's own `.main` catalog) and `Assets.xcassets/` (17-slot `AppIcon.appiconset`). Declared in core's `CheckStitchCore/Package.swift:9` as a supported platform `.watchOS("26.0")`. The `CheckStitchWatch` `PBXNativeTarget` (`project.pbxproj:211-229`) is embedded with `WKWatchOnly = NO` (iOS builds embed `CheckStitchWatch.app` into the iOS archive, `project.pbxproj:14`). Built via `CheckStitchWatch.xcscheme`; `scripts/run-watch.sh` installs/launches on the paired watch.
- `CheckStitchWatchApp.swift:3-12` `@main struct CheckStitchWatchApp: App` — the only view-model wiring point: `@State private var store = WatchChecklistStore(transport: WatchSyncAdapter())` (:6), then `WindowGroup { WatchChecklistListView() }` with `.environment(store)` and `.environment(\.locale, AppLocaleState.current.effectiveLocale)` (:8-10). No delegate adaptor, no `scenePhase`, no coordinator, no `@AppStorage` — unlike the iOS/macOS `MyApp.swift`.
- View logic → core: `WatchChecklistListView.swift:1` imports CheckStitchCore, reads `store.checklists` (:15-17), renders `ContentUnavailableView("No checklists", …)` when empty (:10-13), `.task { store.start(); store.requestRefresh() }` (:27-30). `WatchChecklistDetailView.swift:1` consumes core `Checklist`/`ChecklistItem` (:10,22), seeds from the pushed `Checklist` and re-reads the live store copy as `current` (:16-18), `visibleItems` filters `!isBlank` (:20-23); its "Create reminders" `Button` calls `store.run(checklist)` (:54-57). `WatchSyncAdapter.swift:1` implements core's `ChecklistSyncTransport` (defined `ChecklistSync.swift:118-124`); `session.delegate = self`, `activate()` (:20-25), `sendUserInfo` via `session.transferUserInfo` (:35-48); `WCSessionDelegate` handlers decode `ChecklistSyncMessage(userInfo:)` and funnel to `onMessage`/`onActivated` (:53-97).
- The core state the watch rides on — `WatchChecklistStore` (`ChecklistSync.swift:216+`), an `@Observable @MainActor public final class` (imports Foundation/Observation, no SwiftUI): `checklists` mirror, `pendingRuns`, bounded `phases` map (`phaseLimit = 32`); `start()`, `run(_ checklist)` (dedups in-flight per checklist, returns a fresh `runID`), `retryPendingRuns()`, `requestRefresh()`, `receive(_ message)` (:278-300). Its `.context` decode uses `ChecklistCodec.classify` and accepts `.loaded` and `.migratable(from >= 2)` payloads (:281-296). Explicitly "never touches EventKit" (:222). Run-protocol types are core: `ChecklistSyncMessage` (5 cases :83-96), `RunResultKind`, `RunResult`, `RunPhase`, `PendingRun` (all `ChecklistSync.swift`); `RunResultKind.init(_ outcome: ReminderRunOutcome)` (:70-77).
- Phone peer of the seam: `ChecklistSyncCoordinator` (`ChecklistSyncCoordinator.swift:11`) pushes context on `start()`/`onActivated` and on `checklistsDidChange()`/`languageDidChange()` (:37-53), encodes the snapshot with `ChecklistCodec`, and turns run requests into `createReminders: (Checklist) async -> ReminderRunOutcome` (:13-25). Diagnostics via `ChecklistSyncDiagnostics` (both watch and phone log).
- Relationship summary: `CheckStitchWatch` is a thin companion — its own Swift files only provide the app struct, two SwiftUI views, the passive `WatchSyncAdapter` transport, and localizable string resources. Model (`Checklist`), codec (`ChecklistCodec`), observable store (`WatchChecklistStore`), protocol (`ChecklistSyncMessage`/`ChecklistSyncTransport`/`RunPhase`/`RunResult`/`RunResultKind`) and the phone's `ChecklistSyncCoordinator` all live in `CheckStitchCore/Sources/CheckStitchCore/`. The watch is a read-only mirror that sends run/refresh requests and renders the phone's `runResult` phases; EventKit and reminder creation stay entirely on the phone/core side.

## Q6: What are the canonical build, test, lint and gate commands and conventions?

### Findings
- Destinations (`Makefile:1-11`): `SIM_FROM_WORKTREE` reads `.simulator_id`; `SIM ?=` falls back to `platform=iOS Simulator,name=iPhone 17`; `MAC_SIM := platform=macOS`; `WATCH_SIM := generic/platform=watchOS Simulator`. `SCHEME := CheckStitch`, `WATCH_SCHEME := CheckStitchWatch`, `CONFIGURATION := Debug`, `DERIVED_DATA := DerivedData`. App paths `APP` (iphonesimulator) and `MAC_APP` (`DerivedData/Build/Products/Debug/CheckStitch.app`).
- Target `build` (`Makefile:20`): `xcodebuild -scheme CheckStitch -destination '$(SIM)' -configuration Debug -derivedDataPath DerivedData build` (iOS Simulator leg). `build-mac` (:30): `platform=macOS` + `CODE_SIGNING_ALLOWED=NO` — the unsigned headless macOS compile leg. `build-mac-signed` (:39): macOS + `-allowProvisioningUpdates` — the runnable team-signed app (AppGroup.entitlements incl. KVS `ubiquity-kvstore-identifier` for iCloud sync). `watch-build` (:48): `-scheme CheckStitchWatch -destination 'generic/platform=watchOS Simulator'` (unsigned, sim-free). `run` (:53): `build` then `bash scripts/run-simulator.sh '$(SIM)' '$(APP)'`. `clean` (:63).
- Test targets: `test` (:55) = `test-unit test-ui`. `test-unit` (:60): macOS destination + `CODE_SIGNING_ALLOWED=NO` + `-only-testing:CheckStitchTests test` — unsigned host run, no simulator boot, no App Group gap; `SWIFT_DEFAULT_ACTOR_ISOLATION` is not set on test targets, so suites opt in per-suite. `test-ui` (:67): builds `-only-testing:CheckStitchUITests test-without-building` (one smoke case) on the dedicated simulator `$(SIM)`.
- Gate (`scripts/test.sh`): `set -euo pipefail`, runs from repo root. Cache reclamation (:8-13). Simulator resolution (:19-42): `SIM_ID_FILE=${SIM_ID_FILE:-.simulator_id}`, precedence `$SIM` > `.simulator_id`; `bash scripts/resolve-sim-udid.sh --require-id "$GATE_DEST"`; a present but unresolvable `.simulator_id` is a hard error (exit 1), absent file degrades silently to the shared `name=`. Simulator lock (:47-89): host-scoped `$TMPDIR/checkstitch-simulator.lock` (mkdir-based; reaps a stale holder via `$LOCK_DIR/pid` kill -0; times out after `LOCK_TIMEOUT=60`); quits `Simulator.app` so no window attaches. Single EXIT trap `gate_cleanup` (:91-102) releases the lock + `xcrun simctl shutdown "$GATE_UDID"` (scoped UDID only, never all/booted). Pre-boot (:110) `xcrun simctl boot "$GATE_UDID"` + `bootstatus … -b` when a UDID resolves.
- Gate order (:116-145): `make build` → `make test` (= unit+UI) → `make build-mac` (macOS slice catches iOS-only API bugs) → `make watch-build` (catches pbxproj/watch-scheme edits) → `bash scripts/tests/run.sh` (unless `GATE_TESTS_SKIP=1`) → `shellcheck scripts/*.sh scripts/tests/*.sh` (fallback `bash -n` per file) → `echo "gate: ok"`.
- Lint/static: `shellcheck` on all `scripts/*.sh` + `scripts/tests/*.sh` (`test.sh:137`); absent shellcheck → `bash -n`. No source linter (no swiftlint).
- `scripts/tests/run.sh`: shell-level regression tests of the gate & helpers (stubs `xcrun`/`make`/`osascript`/`defaults`), including the `macos_slice_requests_outgoing_network` awk check (`run.sh:332`) that any pbxproj buildSettings block enabling `ENABLE_APP_SANDBOX` also sets `ENABLE_OUTGOING_NETWORK_CONNECTIONS`.

## Cross-Cutting Observations
- CheckStitchCore already holds the model layer, the EventKit seams, the checklist creator, and a **single** view model (`ChecklistViewModel`) scoped to the creation flow; the run path (destination targeting) has no core view model — its types are protocols/seams shapes only.
- Structural difference vs the mirror: SingleThread keeps every `*ViewModel` **out of** its Core package (they live in the app + watch targets), whereas CheckStitch placed its one partial `ChecklistViewModel` **inside** CheckStitchCore.
- Both repos keep the EventKit seams core-side and test against fakes so suites never touch EventKit; the watch is a read-only mirror in both.
- CheckStitchWatch is thinner than SingleThreadWatch: it has no local app/watch view models (SingleThread has `WatchAppViewModel` + `WatchReminderViewModel` + `Show*State` holders); CheckStitch's watch leans entirely on `WatchChecklistStore` in core.
- Settings orchestration in CheckStitch (`SettingsBindings`, `SettingsDataActionQueue`) lives in the app target, not core, which is consistent with SingleThread leaving settings-side VM code in the app target.
