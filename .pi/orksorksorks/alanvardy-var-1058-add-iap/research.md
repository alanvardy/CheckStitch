# Research Findings

## Q1: How does the checklist "run" flow work end-to-end?

### Findings
- **Three entry points** all converge on the app seam `ChecklistReminders.create(from:)` and the core policy `ChecklistCreator.create`:
  1. **UI button** — `ChecklistRunViewModel.createReminders(for:)` (`CheckStitch/ChecklistRunViewModel.swift:32`), triggered from `ContentView.swift:503-505` (`createRemindersButton(for:)` → `Task { await runVM.createReminders(for: id) }`), rendered at `:444`.
  2. **Voice/shortcut intent** — `CheckStitch/Intents/RunChecklistIntent.swift:53-58` looks up the checklist, pre-checks `targeting.accessStatus()` (dialogue on notDetermined/denied, never prompts), then `await ChecklistReminders.create(...)` and maps outcome → speech (`:79-80`).
  3. **Remote/sync coordinator (iOS)** — `ChecklistSyncCoordinator.handle(.runChecklist(id, runID))` (`CheckStitchCore/.../ChecklistSyncCoordinator.swift:98-118`) dedupes via `rememberedResults[runID]` (re-ack, `:76-83`) and `inFlightRunIDs` (`:84-86`), chains `pendingRun` Tasks so overlapping runs never hold two EventKit stores, then invokes the injected `createReminders(checklist)` closure (`:100-102`). Coordinator built in `MyApp.swift:91-96`.
- **`ChecklistRunViewModel`** (`@MainActor @Observable`): `createReminders(for:)` has an in-flight guard `guard !creating.contains(id), let checklist = store.checklist(id: id)` (`:33`), inserts id into `creating` (`:34`), awaits `ChecklistReminders.create(from: targeting:)`, then on `.created(count)` shows a success flash in `created` set and holds 1s (`:41-45`); `.destinationMissing/.permissionDenied/.partiallyCreated/.failed` set `runErrorMessage` (`:46-48`, cleared via `clearRunError()` `:53-54`). Error alert bound in `ContentView.swift:161-168`.
- **`ChecklistReminders`** (app seam, `CheckStitch/ChecklistReminders.swift`): `:13` prod entry uses `EventKitReminderDestination.shared`; sequencing `:18-54` — `requestAccess()` else `.permissionDenied` (`:20`); snapshot + `destination = snapshot.resolve(checklist.destinationListIdentifier)` else `.destinationMissing` (all-or-nothing, `:21-24`); loop non-blank items (`:25`), number via core `ChecklistTitleNumbering.title` (`:28-32`), `targeting.create(...)` (`:33-39`); returns `.created(count)` (`:40`); catch `:41-53` → `.partiallyCreated(created,total,reason)` if `created>0` else `.failed(reason)`.
- **`ChecklistCreator`** (core policy, `CheckStitchCore/.../ChecklistCreator.swift:30`): mirrors the same policy over the `ReminderCreating` seam (injected, `:8`) — `create(from items)` does `requestAccess()` else `.permissionDenied` (`:31`), drops blanks, assigns position (`:32-34`), per-item `reminders.create(...)` (`:35`), `.created(count)` (`:39`), catch → `.failed` (`:40-42`). Only non-test call is the app seam above.
- **Real adapter** — `EventKitReminderDestination` (`CheckStitch/EventKitReminderDestination.swift`): `:17` `requestAccess()`; `:21-22` `accessStatus()` reads `EKEventStore.authorizationStatus` (status-only); `:40-61` `create(...)` re-resolves the calendar (throws `listMissing` on rename/delete, `:44-47`), builds `EKReminder`, and `#if !os(watchOS)` `eventStore.save(reminder, commit: true)` (`:55-58`) — watchOS EventKit is read-only and never reaches it.
- **Run "completed"** = `createReminders` returns; UI marks success on `.created(count)` + `creating.remove(id)`; remote marks completion after `inFlightRunIDs.remove(runID)` + acks via `transport.sendUserInfo(.runResult(result))` (`ChecklistSyncCoordinator.swift:109-118`).

## Q2: What durable persistence mechanisms exist for small state?

### Findings
- **App Group `UserDefaults` suite** — `CheckStitch/AppGroup.swift:6-10`: `enum AppGroup { static var defaults: UserDefaults { UserDefaults(suiteName:) ?? .standard } }`, `suiteName = "group.app.alanvardy.CheckStitch"` (`:7`), fallback to `.standard` on unregistered simulators/previews (`:2-4`). Enabled by `CheckStitch/AppGroup.entitlements:7-10` (`com.apple.security.application-groups`) and `:11-13` (`com.apple.developer.ubiquity-kvstore-identifier` → `$(TeamIdentifierPrefix)app.alanvardy.CheckStitch`).
- **`@AppStorage` view prefs** — `ContentView.swift:11-17` persist small display prefs (`appearanceMode`, `backgroundEnabled`, `backgroundFadePercent`, `backgroundPinned`, `textSize`, `allowsLandscape`) via plain `UserDefaults.standard` (not App Group/KVS).
- **Core `<X>Preference` struct wrapper** — the reusable convention for a single small value, injectable `defaults`/`key`: `CheckStitchCore/.../AppLanguagePreference.swift:6-29` (validated `rawValue` getter `:13-16`, `setRawValue` → `defaults.set(...)` `:20-22`, `load()` with fallback `:18-19`); `CheckStitchCore/.../AppearanceMode.swift:95-120` same pattern, `load(from:)` `:82-86` mirrors `@AppStorage` fallback. Defaults/key injectable so tests isolate via a UUID-named suite; non-View sites share `static let defaultsKey`.
- **`ChecklistStore`** (`CheckStitch/ChecklistStore.swift`, `@Observable`) — `init(defaults: UserDefaults = AppGroup.defaults, key: "checklists.v1", textEditDelay: Duration? = .milliseconds(300), now:)` (`:63-66`); loads via `defaults.data(forKey:)` + `ChecklistCodec.classify` (`.loaded/.migratable/.unsupportedVersion/.unreadable`, `.unsupportedVersion` → read-only so newer payload survives, `:70-101`); per-install stable ID under `"checklist.deviceID"` (`:89-94`, key `:111`); `envelope` is the only encoded thing and `save()` persists via injected defaults (`:42-47`, `:84-90`).
- **`NSUbiquitousKeyValueStore` sync** — `ChecklistSyncing` protocol + `UbiquitousChecklistSync` adapter (`CheckStitchCore/.../ChecklistSyncing.swift`): protocol `read()/write()/synchronize()/startObserving()` (`:7-16`); adapter `init(store: NSUbiquitousKeyValueStore = .default, key: "checklists.v1")` (`:22-30`), `store.data(forKey:)`/`set`/`synchronize()` (`:32-33`), `startObserving` hooks `NSUbiquitousKeyValueStore.didChangeExternallyNotification` on `.main` (`:35-42`, cancel `:49-59`).
- **Coordinator** `ChecklistSyncService` (`CheckStitch/ChecklistSyncService.swift`) — `start()` wires external-change observer → `reconcile()` and `store.onChange` → `schedulePush()` (debounced 500 ms) (`:59-68`, `:50-51`); `syncOnLaunch()` synchronizes before first read (`:72-78`); `pushNow()` synchronous bypass on backgrounding (`:117-127`).
- **No dedicated counter store exists** — small-value persistence is entirely `UserDefaults`/KVS through the above paths. (Q2 explicitly named only these; no events/counter mechanism was found.)

## Q3: How is app-level state layered and injected across targets?

### Findings
- **Single-process model**: iOS and macOS share one `MyApp` process; watchOS is a separate `@main` app (`CheckStitchWatch/CheckStitchWatchApp.swift:5-7`).
- **iOS/macOS (`CheckStitch/MyApp.swift`)**: singletons declared `@State` (`:21-27`); `init()` builds `store = ChecklistStore()`, then `ChecklistSyncService(sync: UbiquitousChecklistSync(), store: store)` + `syncService.start()` (`:33-45`); each VM takes `store` as a constructor arg (`:38-43`). `body` injects everything on the root in both macOS (`:56-64`) and iOS (`:78-86`) branches via `.environment(...)` (store, five VMs, syncService, `\.locale`). iOS-only: coordinator wired in a `.task` + `.onChange(of: store.checklists)` → `coordinator?.checklistsDidChange()` and `.onChange(language)` (`:88-114`). Both flush on `scenePhase != .active` → `store.flushPendingSave(); syncService.pushNow()` (`:67-71`, `:115-119`).
- **Views consume injected state**: views declare `@Environment(Type.self)`; `ContentView.swift:7-13` reads all seven singletons; detail/edit/export views pull `ChecklistStore` directly (`ChecklistDetailView.swift:9`, `ItemEditView.swift:16`, `ExportChecklistsView.swift:7`).
- **Reactivity**: shared objects are `@Observable`; views use `.onChange(of:)` and mutate back through the VM — e.g. Settings stores edits in `settingsVM`, root re-applies via `.onChange` (`ContentView.swift:554-558`), `applySettings` at `:560-565`, `settingsSnapshot()` `:567-574`. `#Preview` rebuilds the whole env (`:626-639`).
- **Gating / unlock patterns**: **none exists** — grep for `locked|purchase|entitlement|premium|iap|paid` across `*.swift` returns only unrelated senses: two-step delete confirmation (`ContentView.swift:236`), `SyncGate` diagnostics telemetry (`ChecklistSyncDiagnostics.swift:8,44-50`), `FetchGate` test actor (`BackgroundTestFixtures.swift:54,85-102`), and `AppOrientation` lock (`AppearanceViewModel.swift:19`). **IAP is greenfield.**

## Q4: Conventions for new stateful services/components and their tests

### Findings
- **Structure**: `CheckStitchCore` is a sources-only SPM package (iOS 18.7 / macOS 27.0 / watchOS 26.0), one `CheckStitchCore` library target (**no Tests/ dir; `swift test` never used**, `CheckStitchCore/Package.swift`). Shared models/protocols/services live under `CheckStitchCore/Sources/CheckStitchCore/`; platform code split into `CheckStitch/` (iOS/macOS views+delegates), `CheckStitchWatch/`, `CheckStitchTests/` (Swift Testing, macOS-hosted), `CheckStitchUITests/` (one XCTest smoke). New files under `CheckStitch/` need **no** `project.pbxproj` edit (`PBXFileSystemSynchronizedRootGroup`).
- **Seam pattern**: services depend on small `public protocol ... : Sendable` seams in Core — `ReminderCreating` (`ReminderCreating.swift:7`), `ChecklistSyncing` + `ChecklistSyncObservation` (`ChecklistSyncing.swift:6,16`), `ReminderDestinationTargeting` (`ReminderDestinationTargeting.swift:91`), `ChecklistSyncTransport` (`ChecklistSync.swift:205`). `@MainActor` on the protocol makes implementations `Sendable`. A service constructor **injects** the protocol plus a `Data`-only payload seam so Core carries no app model (`ChecklistSyncing.swift` comment). Concrete adapters live per-platform (`PhoneSyncAdapter.swift:1` `#if os(iOS)`; `UbiquitousChecklistSync` in Core; `WatchSyncAdapter`/`WatchChecklistStore` in `CheckStitchWatch/`).
- **Assembly**: a single concrete object wires `Protocol` + `store` + optional `Duration` in a constructor with defaults (`ChecklistSyncService.init(sync: any ChecklistSyncing, store: ChecklistStore, pushDelay: Duration? = .milliseconds(500))` at `ChecklistSyncService.swift:26`); state exposed via `private(set) var isSyncing`/`lastOutcome` (`:12-13`); explicit `start()` subscribes observers. `AppEnvironment` is the "minimal dependency container" (`CheckStitchCore/Environment.swift:3-15`).
- **Tests**: Swift Testing suites `struct <Thing>Tests`, `@Test`/`#expect`, behaviour-named methods, `@Test(arguments:)` tables, `@MainActor` on suites touching EventKit/view models, `@Suite(.serialized)` where shared. Fakes/fixtures in `CheckStitchTests/TestFixtures.swift` (`makeIsolatedDefaults`, `SpyReminderCreator`, `SpyReminderDestination`, `InMemoryChecklistSync`, `@MainActor sharedTestEventStore`) and `BackgroundTestFixtures.swift`. `@testable import` both targets. Tests deliberately don't set actor isolation; suites opt in.
- **Per-platform gating**: `#if os(iOS/macOS/watchOS)` whole-file and in-line guards (`PhoneSyncAdapter.swift:1`, `AppDelegate.swift:1,72`, `MyApp.swift:3,6`, `ContentView.swift:44-406`; tests `MacWindowFrameTests.swift:1`, `InterfaceSettingsViewTests.swift:12,29`, `CheckStitchUITests.swift:34`).
- **Where a cross-cutting service naturally lives**: common protocol + state machine + store logic in `CheckStitchCore/Sources/CheckStitchCore/` with a protocol seam for transport/persistence; platform adapter in `CheckStitch/` or `CheckStitchWatch/`; tested by a Swift Testing suite under `CheckStitchTests/` with fakes in `TestFixtures.swift`.

## Cross-Cutting Observations
- **Single chokepoint**: every run (UI, intent, coordinator) ultimately calls `ChecklistReminders.create(from:)` after `ChecklistRunViewModel`/coordinator orchestration — this is the natural convergence for per-run side effects, but `ChecklistCreator` in Core is the policy owner and has its own call path used by tests.
- **App Group is the shared durable home**: the App Group `UserDefaults` suite (`group.app.alanvardy.CheckStitch`) already backs `ChecklistStore` (key `checklists.v1`) and is where a durable cross-target counter most naturally reads/writes, versus per-install `UserDefaults.standard` used by `@AppStorage` prefs.
- **`@MainActor @Observable` + protocol-seam + `.environment` injection** is the dominant architectural idiom across every feature; a new purchasing/entitlement service would follow it.
- **watchOS is a constrained, separate surface**: no scenePhase, no coordinator, no syncService; EventKit is read-only. Any cross-device entitlement/count consideration must account for the watch's independent `@main` and read-only EventKit.

## Open Areas
- Exact `RunResultKind(ReminderOutcome)` mapping and watch-side handling of `runChecklist`/`runResult` were not verified within budget (Q1).
- No dedicated event/counter or purchase/entitlement surface exists anywhere in `*.swift` — persistence and gating are entirely greenfield (confirm before relying on any hidden IAP wiring).
- Whether the App Group suite is writable on watchOS and whether KVS sync covers a counter (vs. only `checklists.v1`) was not resolved in these traces; the locator confirmed the App Group + KVS entitlements but their watchOS reachability is unchecked.
