# Research Findings

## Q1: How does `scripts/test.sh` drive the build/test legs, detect failures, and handle output?

### Findings
- **Gate sequence** (`scripts/test.sh:1` `#!/bin/bash`, `set -euo pipefail` at :3, `cd` to repo root at :6): optional cache reclaim (:12), simulator resolution via `bash scripts/resolve-sim-udid.sh --require-id "$GATE_DEST"` (:31), `make build` (:40), `acquire_lock()` (:50-60, mkdir lock `${TMPDIR:-/tmp}/checkstitch-simulator.lock`, stale-PID reaping :57-61), `trap 'gate_cleanup' EXIT` (:94), quit Simulator.app (:95), pre-boot `xcrun simctl boot`/`bootstatus` (:98-100), `make test` (:105) → `test: test-unit test-ui` (`Makefile:59`), `release_lock` (:106), `make build-mac` (:111), `make watch-build` (:115), `bash scripts/tests/run.sh` unless `GATE_TESTS_SKIP=1` (:117-119), shellcheck or `bash -n` (:121-126), `echo "gate: ok"` (:127).
- **Failure detection** is `set -euo pipefail` only — no per-leg exit-code checks, no status accumulation; success is implied by reaching :127. The sole explicit `if !` is UDID resolution (:31, `exit 1` "does not name a valid simulator UDID" :33-34). Tolerated failures use `|| true`/guards (:12, :58-61, :77-78, :89, :95, :99) and lock-timeout degradation (:64-66).
- **Gate's own "warning" emissions** (exactly 3, all `>&2`): `:65` "warning: simulator lock busy after ${LOCK_TIMEOUT}s — running without it", `:102` "warning: no worktree simulator id — skipping pre-boot and shutdown", `:124` "warning: shellcheck not installed — skipping script lint". `:45` has "warning" only in a prose comment. Repo-wide `grep -rn warning scripts/` returns only these four hits — any naive grep on gate output will false-positive on :65/:102/:124.
- **xcodebuild output is wholly uncaptured**: all four make legs stream to the gate's console (no `tee`, no `>`, no log). The Makefile recipes do the same (`Makefile:18-21, 31-35, 41-45, 51-53, 65-73, 76-83`). Only redirects are `2>/dev/null` on auxiliary commands (simctl, osascript, version probes). `.github/workflows/dependabot-checks.yml` runs the legs as separate steps straight to the Actions log — it does **not** run the `scripts/test.sh` gate (only individual legs + `run.sh` + shellcheck, `.github/workflows/dependabot-checks.yml:49-74`).

## Q2: Which exact app-source constructs produce the two warning kinds?

### Findings
- **"result of call to 'refresh()' is unused"** — single app site: `CheckStitch/ContentView.swift:100` `.refreshable { await syncService.refresh() }`. The callee `CheckStitch/ChecklistSyncService.swift:77` `func refresh() async -> SyncOutcome` is non-void; the Void-returning `.refreshable` closure discards the awaited `SyncOutcome` (final expression of the closure).
- **`ChecklistStore.swift` has no `refresh`-related warning source**: case-sensitive grep over the file yields zero `refresh` matches (verified this session). The `large.md:23-26` attribution of a second refresh warning to ChecklistStore.swift could not be located in source — likely a duplicated per-leg line reference (the same warning reported in both the iOS-sim and macOS legs).
- `ContentView.swift:173` `await backgroundImage.refreshIfNeeded()` is the same discard-result shape but a different function (`BackgroundImageStore.swift:98`, returns Void) — not warning-producing, but a sibling pattern.
- **Trailing-closure candidate sites** (compiler output not committed; attribution inferred from shape by Q2's researcher): ContentView.swift:104, :182, :215 — three identical `Button("OK", role: .cancel) {}` empty trailing closures inside `.alert(...) { ... }` content blocks where the alert's `{` abuts a `)` on the same line (:103 `})) {`, :181 `) {`, :214). ChecklistStore.swift:353 `for offset in offsets.sorted(by: >) {` and :371 `for index in offsets.sorted(by: >) where checklists.indices.contains(index) {` — statement-body `{` directly after a call's `)`; ChecklistStore.swift:259 `if !taken.contains(where: { sameName($0, candidate) }) { return candidate }` is the only other same-line `)→{` boundary. Which of these the compiler actually flags needs confirmation from a real leg run (see Open Areas).

## Q3: Which exact test-suite lines produce the warning kinds, and how are the frameworks used?

### Findings
- **Framework split within one target**: `CheckStitchTests/ChecklistStoreTests.swift:1-6` is XCTest (`import XCTest`, `@testable import CheckStitch`, `import CheckStitchCore`, `@MainActor final class ... : XCTestCase`); `WatchChecklistStoreTests.swift:2-6` and `ChecklistImportSessionTests.swift:1-5` are Swift Testing (`import Foundation`, `import Testing`, `@MainActor struct`, `@Test`, `#expect`, `try #require`).
- **"redundant #require(_:_:)" — exactly 4 sites**, all `let runID = try #require(store.run(checklist))` in `WatchChecklistStoreTests.swift`: :59, :142, :158, :183. Why redundant: `WatchChecklistStore.run()` returns a non-optional `UUID` (`CheckStitchCore/Sources/CheckStitchCore/ChecklistSync.swift:281-282`), so `#require` (an optional/throwing unwrap macro) is a no-op whose synthesized annotation is flagged. The fifth `#require` at `WatchChecklistStoreTests.swift:230` unwraps a genuine optional and is fine. The recon's "8×" count double-counts each macro site (warning + "was produced here" annotation note).
- **"unused immutable-value initialization" — exactly 4 sites**: `ChecklistImportSessionTests.swift:82` (`let v1 = try session.prepare(...)`, later "use" only in the string "v1 payload migrates and inserts" at :84), `:88` (`let v2`, string at :90), and `ChecklistStoreTests.swift:1295-1296` (`let hardware = store.create(name: "Hardware")`, `let travel = store.create(name: "Travel")` in `testMoveChecklistsPreservesChecklistIdentity`, never referenced). `ChecklistStoreTests.swift:1146` `let travel = store.checklists.first { ... }` is a different, referenced binding. No unused `created` binding exists in the three suites (recon's mention is not findable).
- **#require idiom across the repo**: `try #require(<throwing-or-optional>)` bound to a `let` is the universal unwrap-or-fail pattern (e.g. `LocalizationTests.swift:15,25,47,73-75,81,86,103,107,112,134`; `ChecklistDetailViewTests.swift:223,246`; `ChecklistSyncServiceTests.swift:144,183`; `ListChecklistsIntentTests.swift:49`; `RunChecklistIntentTests.swift:29`; `ChecklistEntityQueryTests.swift:72`) — only the four `store.run` sites apply it to a non-optional.

## Q5: Shell harness, shared scheme, "warning" strings

### Findings
- **`scripts/tests/run.sh`** is a self-contained regression harness (header :1-4, `set -euo pipefail` :5, PASS/FAIL counters :6-7, EXIT trap cleanup :10-14). `new_stubs <names>` (:22-35) writes PATH-inserted stub scripts (xcrun, make, defaults, open, osascript, xcodebuild) that log argv to `$STUB_ROOT/<name>.log`; `run_case` (:36-43) drives pass/fail. Cases cover: `resolve-sim-udid.sh` (5 cases :50-90, xcrun stub), test.sh pre-boot/shutdown (gate children run with `GATE_TESTS_SKIP=1` and stubbed make; :101-123), lock semantics (:132-174 — private `TMPDIR` so the live host lock is untouched; asserts "simulator lock busy after 1s", invalid-UDID error, stale-lock reap), window handling (:176-190), `run-watch.sh` (:205-252, devices.json fixture + devicectl stub), `run-devices.sh` watch path (:254-302, pre-created app dirs under `$STUB_ROOT/dd/Build/Products/`), and a macOS-sandbox awk check on pbxproj (:307-330). Wired into the gate at `scripts/test.sh:117-119`; CI mirrors it (`.github/workflows/dependabot-checks.yml:65`).
- **Committed shared scheme**: `CheckStitch.xcodeproj/xcshareddata/xcschemes/CheckStitch.xcscheme` lists both testables (`parallelizable="NO"`, `skipped="NO"`, TestAction :26-59) — serial execution gives deterministic ordering; `shouldAutocreateTestPlan="YES"` (:33). `CheckStitchWatch.xcscheme` sits beside it. Makefile pins schemes/destinations per leg (`-only-testing:` one suite per leg, shared `-derivedDataPath DerivedData`, Debug; `Makefile:45-53, 55-67`).
- **Repo-wide "warning" string inventory** (excluding `.pi/`, `DerivedData/`, `.git/`): gate's three `echo "warning: ..."` (`scripts/test.sh:65, 102, 124`); `CheckStitchCore/Sources/CheckStitchCore/ChecklistSyncDiagnostics.swift:59,76` `logger.warning("[diagnostics] ...")`; a source comment `CheckStitchTests/StubBundle.swift:7` ("Swift 6 + warnings-as-errors rejects subclasses..."). Nothing in `scripts/tests/run.sh`, `scripts/resolve-sim-udid.sh`, `scripts/run-*.sh`, Makefile, `.github/`, docs. `DerivedData/` hits are false positives (build paths).

## Cross-Cutting Observations
- **Single warning vocabulary**: all *source* warnings come from two Swift constructs (`discarded non-void result in a void closure`, `ambiguous trailing closure`), and all *test* warnings from two macro/idiom habits (over-used `#require` on non-optionals, worthless `let` bindings). The count mismatch between the recon (8×/8×) and current source (4×/4×) is explained by double-counting each macro site (warning + produced-annotation) — per-site tallies agree.
- **No instrumentation exists to observe warnings**: no log capture in the gate, Makefile, or CI; warning-as-error flags are absent everywhere. Any future check must add capture/flag machinery as new infrastructure.
- **The gate's own `warning:` stderr lines (3) and the AppIntents metadata note are the two non-source warning sources**; AppIntents appears in 3 of 4 legs and is toolchain-level (its literal never appears in repo files).
- **Determinism is a design value here**: serial `parallelizable="NO"` scheme, per-suite `-only-testing:` legs, shared `-derivedDataPath`, `set -euo pipefail` — consistent with a scanfail gate; the macOS-sandbox awk check shows the pbxproj is treated as assertable config.
