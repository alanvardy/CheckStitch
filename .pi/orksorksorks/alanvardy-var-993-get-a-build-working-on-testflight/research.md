# Research Findings

## Q1: Build pipeline — Makefile targets, xcodebuild invocations, destinations, iOS artifacts

### Findings
- **Config defaults**: `SCHEME := CheckStitch` (Makefile:9), `CONFIGURATION := Debug` (Makefile:10), `DERIVED_DATA := DerivedData` (Makefile:11). `WATCH_SCHEME := CheckStitchWatch` (Makefile:8).
- **Destination resolution** (Makefile:4-7): `SIM_FROM_WORKTREE` reads `.simulator_id` → `platform=iOS Simulator,id=<udid>`; `SIM ?= $(if $(SIM_FROM_WORKTREE),…,platform=iOS Simulator,name=iPhone 17)`; `MAC_SIM := platform=macOS` (Makefile:6); `WATCH_SIM := generic/platform=watchOS Simulator` (Makefile:7). Explicit `SIM=` (env/CLI) always wins.
- **iOS artifact paths**: simulator app `DerivedData/Build/Products/Debug-iphonesimulator/CheckStitch.app` (Makefile:13); device app `DerivedData/Build/Products/Debug-iphoneos/CheckStitch.app` (scripts/run-devices.sh:36); macOS `DerivedData/Build/Products/Debug/CheckStitch.app` (Makefile:14); watch `DerivedData/Build/Products/Debug-watchos/CheckStitchWatch.app` (scripts/run-watch.sh:31).
- **Targets**:
  - `build` (Makefile:17-23): `xcodebuild -scheme CheckStitch -destination '$(SIM)' -configuration Debug -derivedDataPath DerivedData build`. Unsigned, simulator.
  - `build-mac` (Makefile:30-36): macOS, adds `CODE_SIGNING_ALLOWED=NO build` — gate's unsigned compile leg.
  - `build-mac-signed` (Makefile:40-46): macOS with `-allowProvisioningUpdates build` — signed runnable macOS app.
  - `watch-build` (Makefile:50-56): `-scheme CheckStitchWatch -destination 'generic/platform=watchOS Simulator'`, unsigned, sim-free.
  - `run` (Makefile:57-58): `build` then `bash scripts/run-simulator.sh '$(SIM)' '$(APP)'`.
  - `test: test-unit test-ui` (Makefile:60); `test-unit` (Makefile:64-71) macOS host `CODE_SIGNING_ALLOWED=NO -only-testing:CheckStitchTests test`; `test-ui` (Makefile:75-86) = `build-for-testing` then `test-without-building -only-testing:CheckStitchUITests`, both on `$(SIM)`.
  - `clean` (Makefile:88-89).
- **Device flavor** (scripts/run-devices.sh:79-84): one build per run, `xcodebuild -scheme CheckStitch -destination 'generic/platform=iOS' -configuration Debug -derivedDataPath DerivedData -allowProvisioningUpdates build`; install/launch via `xcrun devicectl device install app` / `process launch` per device (run-devices.sh:92-104). macOS leg calls `make build-mac-signed` + `open` (run-devices.sh:110-121).
- **Watch flavor** (scripts/run-watch.sh:83-105): resolves watch by name from `devicectl list devices -j` (NFKC/apostrophe folding, run-watch.sh:40-72), never a bare name; builds `-destination 'generic/platform=watchOS' … -allowProvisioningUpdates`, then install/launch. Watch bundle id `app.alanvardy.CheckStitch.watchkitapp` (run-watch.sh:22).
- **Simulator resolution**: `scripts/resolve-sim-udid.sh` — `,id=` extracted verbatim (resolve-sim-udid.sh:21-22); `name=` resolved via `simctl list devices available` (resolve-sim-udid.sh:24-27); `--require-id` rejects unpinned names (resolve-sim-udid.sh:31-33) and validates UUID regex (resolve-sim-udid.sh:34-37). Gate calls it with `--require-id` (test.sh:24).
- **Flavor signing summary**: iOS simulator builds unsigned; macOS split unsigned-compile vs signed-runnable; iOS device and real-watch builds signed via `-allowProvisioningUpdates`. Device build differs from simulator only in destination (`generic/platform=iOS` vs `id=`-pinned simulator) and the provisioning flag.

## Q7: App Store Connect / TestFlight — documented delivery surface (web research, sourced)

### Findings (source URLs in the full researcher report; all from Apple's docs)
- **Two delivery routes**: (1) Xcode Cloud build — Apple's hosted CI/CD that builds, signs, and submits archives to App Store Connect automatically; (2) upload a locally produced archive via Xcode Organizer, Xcode Cloud, Transporter (CLI on macOS/Windows/Linux), `xcrun altool --validate-app/--upload-app`, or the App Store Connect API ([distributing-app-for-beta-testing](https://developer.apple.com/documentation/Xcode/distributing-your-app-for-beta-testing-and-releases), [upload-builds](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds)).
- **Local flow**: Archive (scheme + device destination) → Organizer → Distribute App → "App Store Connect" method → **Upload** (to ASC) or **Export** (local .ipa for later upload). Export allows distributing outside the App Store; upload-through-ASC distributes via TestFlight or the App Store.
- **Artifact requirements**: uploads associate to the app record via **bundle identifier + version** in the app bundle; each upload needs a unique build number; **first upload of an app creates a beta version**; builds are processed by Apple before appearing (email on completion). iOS builds must be built with Xcode 16+ (Xcode 14+ required for uploads from 2026).
- **Signing**: TestFlight-eligible builds must be **signed for App Store distribution** — an Apple Distribution certificate and an App Store-type provisioning profile, produced by archiving **for a device, not a simulator**; "automatically manage signing" is the documented Xcode path; App Store Connect manages certificate access.
- **Roles/API/testers**: upload roles Account Holder/Admin/App Manager/Developer; the App Store Connect API exposes "Prerelease Versions and Beta Testers" resources (Beta Testers, Beta Groups, invitations, prerelease versions, build–group assignment) all behind a signed JWT from an ASC API key; WWDC25 introduced a Build Upload REST flow (create BuildUpload → BuildUploadFile → PUT binary → notify → build processes to COMPLETE). Internal testers ≤100 (no Beta App Review); external ≤10,000 (email/CSV/public link; first build of each version needs Beta App Review).

## Cross-Cutting Observations
- **Signing is fully declarative**: Automatic style + team `6NWX2DHB9Q`, no identities/passwords in scripts; provisioning profiles fetched implicitly through `-allowProvisioningUpdates` (CheckStitch) or not at all (SingleThread). The macOS ASC distribution path is proven in SingleThread (`method = app-store-connect` exportOptions.plist), but **no iOS distribution/archive exists in either repo** — the documented TestFlight requirement (device archive, App Store distribution signing) does not map to any existing target, since every current iOS build is a Debug simulator/device build with team signing.
- **Gate constraints that any CI must honor**: .simulator_id pinning with --require-id (never bare name=), the shared /tmp simulator lock, single EXIT trap + scoped shutdown, Simulator.app quit, and the signed macOS leg staying provisioning-free (`CODE_SIGNING_ALLOWED=NO`) — the unsigned legs exist to keep the gate machine-independent.
- **Conventions that must survive**: `scripts/*.sh` are `#!/bin/bash` + `set -euo pipefail`, mode 100755, covered by scripts/tests/run.sh instances; GENERATE_INFOPLIST_FILE=YES means Reminders/EventKit usage descriptions are `INFOPLIST_KEY_*` build settings; App Group/KVS entitlements live only in `CheckStitch/AppGroup.entitlements`.
- **The repo has no CI and no GitHub Actions at all** (no `.github/`); SingleThread's ci.yml is the only in-house example, and it neutralizes signing rather than performing it — so there is no committed pattern for a signing/uploading CI step anywhere.
- **Bundle id/version are the ASC join keys**: `app.alanvardy.CheckStitch` + `MARKETING_VERSION 1.0` are what an uploaded build will be matched to in App Store Connect.

## Open Areas
- **Which RHS machine owns ASC credentials, the distribution certificate, and the provisioning profile** — no repo evidence; SingleThread's runbook says the portal (IAP entitlement on the Mac App ID) is not yet fixed for signed archive/export, and its macOS profile predates IAP.
- **Device-archive mechanics**: whether `xcodebuild archive -destination 'generic/platform=iOS' -configuration Release` with current settings produces an ASC-acceptable IP archive (or whether provisioning profile specifiers / a distribution certificate are required first) — unfindable from repos alone; the Q7 build-upload reference pages (Build Upload API schemas, Transporter package formats, live Upload-builds page) were not fetched in full within budget.
- **Cloud vs prebuilt upload decision data points**: Xcode Cloud requires Apple Build accounts/quotas and is a brand-new surface; Transporter/altool/API upload of a locally archived .ipa is the lower-touch path, but the exact `.ipa` contents Apple accepts for TestFlight (vs App Store) are only documented at the level cited in Q7.
- **Version/build-number hygiene**: `MARKETING_VERSION = 1.0` and `CURRENT_PROJECT_VERSION = 1` are static in pbxproj; nothing in-repo derives unique build numbers (ASC requires a unique build number per upload).
