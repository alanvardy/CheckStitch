## Cross-Cutting Observations
- **Companion model, not standalone**: SingleThread's watch is a companion to the iOS app — embedded via `Embed Watch Content`, `WKCompanionAppBundleIdentifier` = iOS bundle id, `WKWatchOnly = NO`, and mutable reminder state syncs phone↔watch over WatchConnectivity because watchOS EventKit is **read-only** (write API compiled out). The watch still reads reminders from its own local EventKit store.
- **watchOS target recipe** (from SingleThread): `SDKROOT = watchos` + `SUPPORTED_PLATFORMS = "watchos watchsimulator"` + `TARGETED_DEVICE_FAMILY = 4` + `WATCHOS_DEPLOYMENT_TARGET` + `PRODUCT_BUNDLE_IDENTIFIER` (suffixed `.watchkitapp`) + `DEVELOPMENT_TEAM` + `CODE_SIGN_STYLE = Automatic` + `GENERATE_INFOPLIST_FILE = YES` + WK/NSReminders infoplist keys; sources included purely via a `PBXFileSystemSynchronizedRootGroup`.
- **Signing split**: iOS/simulator configs carry `CODE_SIGN_ENTITLEMENTS` (AppGroup file); watch configs rely on team-based automatic signing with no entitlements file.
- **CheckStitch already has** the Reminders infoplist usage descriptions, `DEVELOPMENT_TEAM`, `AppGroup.entitlements`, and even a project-level `WATCHOS_DEPLOYMENT_TARGET = 27.0`; what it lacks is any watch target, watch make targets, and a watch UI.
- `GENERATE_INFOPLIST_FILE = YES` in both projects: all usage descriptions live as `INFOPLIST_KEY_*` build settings.
- Deployment state of the art is simulator + physical iOS devices; the physical watch (`Alan's Apple Watch`, paired, reachable) has no existing install/launch script anywhere.

- CheckStitch's checklist data model is a Reminders list whose items are each a Reminder in the default reminders calendar; how those map to the watch's list/read flow (vs SingleThread's skip/completion semantics) is unexamined.
- The `--ui-testing` arg handling inside the watch app entry point was not located within budget (the seam exists in `WatchAppViewModel`).
