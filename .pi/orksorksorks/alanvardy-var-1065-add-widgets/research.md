## Q3: Persistence and ownership of the checklist store

### Findings
- `ChecklistStore` is an `@Observable final class` in the **app target** (`CheckStitch/ChecklistStore.swift:3`), not Core. Init `defaults: UserDefaults = AppGroup.defaults, key = "checklists.v1", textEditDelay = 300ms` (`:49-52`). Storage = single UserDefaults key `checklists.v1` holding a versioned `ChecklistEnvelope` (`:104-111`, encoded by `ChecklistCodec`).
- On init: reads/classifies payload, migrates v1/v2/v3, `unsupportedVersion` (newer payload → `canOverwriteStoredPayload=false`, in-memory-only mutations, saves refused), `unreadable` (`:72-101`). Stable per-install `deviceID` UUID stamped into every envelope (key `checklist.deviceID`, `:55-63,118`).
- App-Group KV: `AppGroup.suiteName = "group.app.alanvardy.CheckStitch"`; `AppGroup.defaults = UserDefaults(suiteName:) ?? .standard` (`CheckStitch/AppGroup.swift:6-11`). Pinned byte-for-byte in `CheckStitch/AppGroup.entitlements` (AGENTS.md; `CheckStitchTests/AppGroupTests.swift:6-12`). Other group-backed stores: `RunCounter(defaults: AppGroup.defaults)` (`ChecklistRunViewModel.swift:16`), `PurchaseEntitlementCache(defaults: AppGroup.defaults)` via `PurchaseEnvironment.service` (`MyApp.swift:133-136`).
- **No singleton** on `ChecklistStore`. App owns one instance in `MyApp.init()`, held in `@State` (`MyApp.swift:34-46`), shared by the list/run/import-export VMs and injected via `.environment(store)` (`ContentView.swift:632-643`). Constructed on the main actor.
- Independent callers open the same store with `ChecklistStore(defaults: AppGroup.defaults)` — exactly what the intents do (`RunChecklistIntent.swift:42`, `ChecklistEntity.swift:28-31` "Fresh store per call when nothing is injected (design decision 7)"). So a fresh instance per call in the same app group is the established pattern.
- KVS sync ownership: `ChecklistSyncService` (`@MainActor @Observable`, `ChecklistSyncService.swift:15-17`): `init(sync:any ChecklistSyncing, store:, pushDelay:)` (`:27-31`); `start()` wires external-change observer + store `onChange` (`:35-43`); `syncOnLaunch()` (`:46-53`). Real adapter `UbiquitousChecklistSync` (`@MainActor`, `Core/.../ChecklistSyncing.swift:20-26`) over one long-lived `NSUbiquitousKeyValueStore .default`, key `"checklists.v1"`; `synchronize()` `:30`; `startObserving` on `.main` queue `:33-43`.
- Construction chain: `MyApp.init()` → `ChecklistSyncService(sync: UbiquitousChecklistSync(), store:)` + `syncService.start()` (`MyApp.swift:35-37`); injected via `.environment(syncService)` (`ContentView.swift:7`). Store refuses remote folding when `canAcceptRemoteChanges` false (`ChecklistStore.swift:113-116`, `ChecklistSyncService.swift:115`).
- Watch path is separate: `ChecklistSyncCoordinator` (`Core/.../ChecklistSyncCoordinator.swift:6`) is the phone side of WCSession (pushes checklists + language, turns watch run requests into reminder creation); watch app owns `@State WatchChecklistStore(transport: WatchSyncAdapter())` (`CheckStitchWatch/CheckStitchWatchApp.swift:6-7`).

## Q5: Widget frameworks on the target OS (web research)

### Findings
- Apple's cross-platform widget framework is **WidgetKit** (SwiftUI-based; iOS 14→26, macOS Big Sur→Tahoe 26, iPadOS, watchOS, visionOS, CarPlay). This is the platform's offering of user-visible widgets with fixed size-class families. UIKit/AppKit views not supported inside widgets. Sources: [Creating a widget extension](https://developer.apple.com/documentation/widgetkit/creating-a-widget-extension), [Building Widgets Using WidgetKit and SwiftUI](https://developer.apple.com/documentation/widgetkit/building_widgets_using_widgetkit_and_swiftui).
- Fixed size classes are grid "families": `.systemSmall` (~2×2), `.systemMedium` (~4×2), `.systemLarge` (~4×4), `.systemExtraLarge` (~8×4; iPad/Mac/visionOS — not iPhone). Declare `.supportedFamilies([.systemSmall, .systemLarge])`; branch per size via `@Environment(\.widgetFamily)`. Small-only+large is a supported subset. [Supporting additional widget sizes](https://developer.apple.com/documentation/widgetkit/supporting-additional-widget-sizes), [HIG Widgets](https://developer.apple.com/design/human-interface-guidelines/widgets).
- Accessory sizes (separate fixed set): `accessoryCircular`, `accessoryRectangular`, `accessoryInline`, `accessoryCorner` — monochrome, non-interactive snapshots for iOS Lock Screen (iOS 16+) and Watch complications, same WidgetKit code. [Creating accessory widgets and watch complications](https://developer.apple.com/documentation/WidgetKit/Creating-accessory-widgets-and-watch-complications), [TechCrunch WWDC22](https://techcrunch.com/2022/06/06/apples-widgetkit-update-lets-developers-build-for-the-lock-screen-and-watch-with-the-same-code/).
- Binding to an app action: (a) deep link `widgetURL(_:)` opens the containing app (`.onOpenURL`); (b) interactive `Button(intent:)`/`Toggle` backed by **App Intents** run the action without launching the app; iOS 26 adds `WidgetPushHandler`. [Adding interactivity to widgets and Live Activities](https://developer.apple.com/documentation/WidgetKit/Adding-interactivity-to-widgets-and-Live-Activities), [widgetURL](https://developer.apple.com/documentation/SwiftUI/View/widgetURL(_:)).
- macOS: same WidgetKit on desktop + Notification Center (Sonoma+). macOS Tahoe 26 adds `ControlWidget` (SwiftUI, macOS 26+) with `ControlWidgetButton`/`ControlWidgetToggle` bound to App Intents, placeable in Control Center (small/medium/large) or menu bar. "Widget packs" is a marketing label, not a distinct API. [ControlWidget](https://developer.apple.com/documentation/swiftui/controlwidget), [WidgetKit updates](https://developer.apple.com/documentation/updates/widgetkit).
- Packaging model: a widget is a separate Xcode **"widget extension"** target whose product is an `.appex` embedded in the app bundle at `PlugIns/` (e.g. `MyApp.app/PlugIns/MyWidgetExtension.appex`) via an "Embed Foundation Extensions" build phase. One extension exposes many widgets via `@main struct ...: WidgetBundle`. The extension is its own distributable: own App ID (prefixed by the app bundle id), own provisioning/distribution profile, own entitlements and signature. [WidgetBundle](https://developer.apple.com/documentation/swiftui/widgetbundle), [Configuring App Groups](https://developer.apple.com/documentation/xcode/configuring-app-groups).
- **In-process vs host**: widgets do **not** run in the app. The system launches the extension on demand in its own sandboxed process (separate file container, ~tens-of-MB ceiling) and renders cached timeline snapshots; the app process is not involved while a widget is on screen. App↔widget data sharing requires an App Group entitlement (`com.apple.security.application-groups`, `group.`-prefixed container id) on **both** targets; app writes / widget reads via shared `UserDefaults(suiteName:)` or a shared file/database container. App Intents run in the extension process by default; only intents with `openAppWhenRun` (or conforming e.g. `AudioPlaybackIntent`, `LiveActivityIntent`) run in the app's process. [Developing a WidgetKit strategy](https://developer.apple.com/documentation/WidgetKit/Developing-a-WidgetKit-strategy).
- iOS 26 surfaces: widgets on Home Screen (user-placed), Lock Screen, StandBy, CarPlay (`systemSmall`); new `\.widgetRenderingMode`/`widgetAccentedRenderingMode`; `.systemExtraLargePortrait` on visionOS/iPad. [WWDC25 session 278](https://developer.apple.com/videos/play/wwdc2025/278/).
- Adjacent surfaces (distinct): **Live Activities** (ActivityKit: `Activity.request/update/end` + `ActivityConfiguration`) render Lock Screen / Dynamic Island real-time content with `activityFamily` sizes (`.supplementalActivityFamilies([.small,.medium])`); on macOS Tahoe and via iPhone Mirroring (iOS 18+). [ActivityKit updates](https://developer.apple.com/documentation/updates/activitykit), [9to5Mac](https://9to5mac.com/2025/06/16/macos-26-live-activities-work-even-if-your-iphone-is-on-ios-18/).
- Gaps: numeric grid units (2×2/4×2/4×4/8×4) and physical point sizes are search-synthesised from HIG mirrors/WWDC notes, not pixel-verified against a fetched Apple page; macOS Tahoe 26 specifics rest on Apple docs + press.

## Cross-Cutting Observations
- **Reusable run primitive**: the only path that materialises reminders is `ChecklistReminders.create(...)` (full `ChecklistReminders.swift:28-67`) and `ChecklistRunViewModel.createReminders(for:)`. Any new surface wanting to "run a checklist" uses one of these plus the run gate — there is no other creation path in the live flow.
- **Established out-of-app pattern**: App Intents already run a checklist outside the app UI with `openAppWhenRun=false`, constructing a fresh `ChecklistStore(defaults: AppGroup.defaults)` per call, using `EventKitReminderDestination.shared`, resolving purchase + `RunGate` via `ChecklistReminders.productionGate()`, and doing a status-only access pre-check (no prompt from a cold process — `RunChecklistIntent.swift:53-54`). This is the direct precedent for a widget extension that must not launch the app.
- **@MainActor dominates**: run VMs, the EventKit destination (singleton `shared`), sync service, and intents are all `@MainActor`. Only the Core `ChecklistCreator` struct is `Sendable`.
- **No existing widget surface** exists in the repo — the widget side is entirely greenfield; only the intent/`EntityQuery` model and the App-Group KV store are reusable.
- **App-Group is the data bridge**: App Group entitlement already exists for the app; Q5 confirms the same entitlement (added to both targets) is exactly what lets a widget extension share the `checklists.v1` payload via `UserDefaults(suiteName:)`.
