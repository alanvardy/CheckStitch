# Research Findings

## Q1: How the checklist export flow works end to end

### Findings
- **Trigger — Settings row → staging.** The Settings sheet's export row calls `onExport: { requestDataAction(.export) }` (CheckStitch/ContentView.swift:498), which stages the action: `settingsVM.stage(action)` (ContentView.swift:530). `SettingsViewModel.stage(.export)` pushes onto a FIFO queue (pinned by `SettingsDataActionQueueTests`). Nothing presents yet.
- **Sheet dismiss + macOS staging delay.** ContentView.swift:106-115: `.onChange(of: settingsVM.showsSettings)` fires as the settings sheet dismisses → `settingsVM.sheetDidDismiss()`, `takeStaged()`; if an action is staged: `Task { try? await Task.sleep(for: .milliseconds(400)); perform(action) }`. The 400 ms sleep is the macOS workaround — a sheet-nested `.fileExporter` never presents on macOS, so the settings sheet must fully dismiss before `perform` asks the root-owned exporter to open (ContentView.swift:109-112 comment). `perform(.export)` → `importExportVM.beginExport()` (ContentView.swift:538).
- **Open the multi-select sheet.** `beginExport()` (CheckStitch/ChecklistImportExportViewModel.swift:26-30): `exportSelection = []`, `isShowingExport = true`. The `.sheet(isPresented: importExportVM.isShowingExport)` presents `ExportChecklistsView` (ContentView.swift:99, 160-167). Multi-select toggles `exportSelection`; `canExport` disables the button when empty.
- **`exportSelected()` builds the document.** ChecklistImportExportViewModel.swift:44-53: clears `isShowingExport`; filters `store.checklists` by `exportSelection`; empty selection → `return` (exports nothing); else `exportDocument = try ChecklistExportDocument(checklists: selected)`; on success `isExporting = true`; on throw sets `exportErrorMessage`.
- **`.fileExporter` presentation.** ContentView.swift:169-177: `isPresented: isExporting` (setter → `dismissExport()`), `document: importExportVM.exportDocument`, `contentType: .json`, `defaultFilename: ChecklistExport.filename()`. Completion `result`: on `.failure` → `importExportVM.exportFailed(error)` (ContentView.swift:172-174).
- **What `ChecklistExportDocument` carries.** CheckStitch/ChecklistExportDocument.swift (SwiftUI `FileDocument`): `readableContentTypes = [.json]` (line 9); `data: Data` (line 11); `init(checklists:)` = `try ChecklistExport.data(checklists:)` (13-15); `init(configuration:)` reads back `configuration.file.regularFileContents` (17-22, read-only; import uses `.fileImporter`, not FileDocument opening); `fileWrapper(configuration:)` returns `FileWrapper(regularFileContents: data)` (24-26). The exporter writes exactly the bytes in `data`.
- **The bytes.** `ChecklistExport.data` → `ChecklistCodec.encode(envelope(checklists:))` (CheckStitchCore/Sources/CheckStitchCore/ChecklistExport.swift:15-17) = `JSONEncoder().encode(_ envelope)`. `envelope` = `ChecklistEnvelope(version: currentVersion, deviceID: "", checklists: <selected subset>, tombstones: [])` (ChecklistExport.swift:8-13). Valid JSON codec payload, no device identity, no tombstones.
- **Filename derivation.** `ChecklistExport.filename(for:calendar:)` (ChecklistExport.swift:21-27): `yyyy-MM-dd` (`en_US_POSIX`), returns `"CheckStitch-YYYY-MM-DD"` (no extension; `.fileExporter` appends `.json` from the content type).
- **`isExporting`** is `private(set)` (ChecklistImportExportViewModel.swift:19), toggled only by `exportSelected()`/`dismissExport()`.

## Q2: Security-scoped resources and on-disk staging today

### Findings
- **The only security-scoped resource use is the import path.** CheckStitch/ChecklistImportExportViewModel.swift:67-80 — `importFile(at url:)` wraps the read in an access/stop pair: `:68-69` `let accessing = url.startAccessingSecurityScopedResource()` / `defer { if accessing { url.stopAccessingSecurityScopedResource() } }`; `:70-74` reads `Data(contentsOf: url)` into a local, mapping read failure to `importErrorMessage`; `:76-84` hands `data` to `ChecklistImportSession(store: store).prepare(data:)`, with format-failure handling.
- **No on-disk staging exists for the export/share path — export is purely in-memory.** ChecklistImportExportViewModel.swift receives the URL from the root view's `.fileImporter` completion (ContentView.swift:176-186, `case .success(let url)`). Security-scoping is entered/exit **synchronously around the read only**; only in-memory `Data` flows onward.
- ChecklistExportDocument.swift:9-28 holds `let data: Data` (`:12`); `fileWrapper` returns `FileWrapper(regularFileWithContents: data)` (`:26-28`). No URL, no temp file, no security scope.
- **The only on-disk file writer in the app is unrelated to export:** CheckStitch/BackgroundImageStore.swift:190-191 (`applicationSupportDirectory`/`CheckStitch` subdir), :255-260 — `FileManager.default.createDirectory` then `imageData.write(to:, options: .atomic)` plus `encoder.encode(metadata).write(...)` — persists wallpapers, not documents.
- `rg` across `CheckStitch/` for `FileManager|write(to|temporaryDirectory|fileURL|cachesDirectory|.tmp|Data.write` returns only BackgroundImageStore hits — no temp/on-disk document construction anywhere in the app target.
- **iOS vs macOS: documented divergence is presentation timing, not physical form.** SwiftUI converts the `FileDocument` → bytes itself; the app never consumes a staged-file URL. ContentView.swift:110-118 (macOS `fileExporter`-in-sheet workaround) and ContentView.swift:124-141 (import/export wiring anchored to root view so panels present on both OSes).

## Q3: Platform gating within the single app target + the macOS workaround

### Findings
- **Platform gating = compile-time `#if os(...)` in the single SwiftUI target.** CheckStitch/ContentView.swift uses `#if os(iOS)` / `#if os(macOS)` / `#endif` throughout; no per-platform file split in `CheckStitch/` for this view.
  - ContentView.swift:44 `#if os(macOS)` — macOS toolbar (`createButtonPlacement` in the title bar; comment 49-51: macOS window actions live in the title bar).
  - ContentView.swift:68 `#if os(iOS)` — iOS NavigationStack `containerBackground(.clear, for: .navigation)` (69-73).
  - ContentView.swift:94 `#if os(macOS)` — macOS `.preferredColorScheme` threading (95-98).
  - ContentView.swift:118 `#if os(iOS)` — iOS floating chrome plates vs macOS toolbar items (119-122).
  - `#if os(iOS)` also in `createButtonPlacement` (ContentView.swift:230 vs `#else` :232), `createButton` :242, `settingsButton` :278, edit toggle :323, content padding :369.
- **The `.fileExporter` + 400ms workaround.** `.fileExporter(isPresented: Binding(...), document: importExportVM.exportDocument, contentType: .json)` lives on the root `ContentView` (ContentView.swift:169-172). ContentView.swift:108-116: on a staged action, `settingsVM.sheetDidDismiss()` (:108), take staged action (:109), comment (:110-112): "The file panels live on this root view: a sheet-nested `.fileExporter` never presents on macOS. So the settings sheet has to finish dismissing before the panel is asked for." Then `Task { try? await Task.sleep(for: .milliseconds(400)); perform(action) }` (:113-116).
- CheckStitch/ExportChecklistsView.swift:4-5 repeats the constraint: a sheet-nested exporter never presents its panel on macOS, so export hands the selection back to the root view that owns `.fileExporter`; the sheet only produces a selection. ContentView.swift:166 `importExportVM.exportSelected()` is the call routed to `perform(action)`.

## Q4: Platform share-sheet / share-dialog APIs (iOS & macOS)

### Findings
- **Two platform architectures.** iOS share sheet is hosted by UIKit's `UIActivityViewController` (presentation in private `ShareSheetUI.framework`/internal `SHSheet*`/`_UIActivity*` classes — not public API). macOS uses AppKit's `NSSharingServicePicker` (macOS 10.8+). SwiftUI `ShareLink` is the cross-platform wrapper, bridging to the UIKit activity VC on iOS and `NSSharingServicePicker` on macOS. (developer.apple.com; mikesusz.dev/blog/what-ios-shares/)
- **SwiftUI invocation + inputs.** `ShareLink(item: someTransferable, subject:, message:, preview:)`; `item` must conform to `Transferable`, whose `static var transferRepresentation` returns a `TransferRepresentation`. Input kinds:
  - `DataRepresentation(exportedContentType:) { item in …Data… }` — raw in-memory bytes; `.suggestedFileName` (iOS 17+) controls the on-disk name. No staging needed.
  - `FileRepresentation(exportedContentType:, shouldAllowToOpenInPlace: false) { item in … }` — closure must **write bytes to a temp file** and return `SentTransferredFile(url)`; `allowAccessingOriginalFile` maps to open-in-place. File staged by the app first; closure is lazy (runs only when a share action is chosen). (developer.apple.com CoreTransferable/FileRepresentation; swiftui/sharelink)
- **macOS AppKit invocation + inputs.** `NSSharingServicePicker(items:)` accepts `String`, `URL`, `NSImage`, `NSItemProvider`, or `NSPreviewRepresentableActivityItem` (macOS 13+ gives a preview popover; macOS 12- shows a menu list). Presented via `picker.show(relativeTo: rect, of: view, preferredEdge:)` anchored to a real `NSView`, via `standardShareMenuItem`, or via `NSSharingServicePickerToolbarItem`. Plain file URL/`NSItemProvider` is the "staged file" route — no public way to hand raw bytes on macOS except wrapping in a provider/file URL. (developer.apple.com AppKit/NSSharingServicePicker; NSPreviewRepresentableActivityItem)
- **Security-scoped consumption.** The share graph is system-brokered; consumers get `NSExtensionItem`s and use `loadItem`/`loadFileRepresentation`/`loadDataRepresentation`. Reading a file URL requires `startAccessingSecurityScopedResource()`/`stopAccessingSecurityScopedResource()` around actual file access. Known pitfalls: `_NSItemProviderSandboxedResource` opaque token instead of `URL` (ask for `public.file-url`); unreadable `file:///private/var/...` URLs from the Files app when no scoped token granted. (developer.apple.com; forums thread 745044; SO 57644782)
- **Presenting from within an open sheet/tab — known constraints.** On macOS, SwiftUI `.sheet` renders as a document-modal child window; a picker popover presented inside becomes a child of that sheet window, so choosing "Save Image"/"Save to Files" tears down the popover *and* the presenting view (Apple forums 818483/818479/797200). Console warnings `NSSharingServicePicker showRelativeToRect… should not be called on mouseUp` and `Unable to simultaneously satisfy constraints` accompany presenting during the mouse-up/update pass; canonical fix is `sendAction(on: [.leftMouseDown])` + call `show()` asynchronously, re-anchoring via the delegate's `anchoringView(for:showRelativeTo:preferredEdge:)` to a main-window view. iOS analogue: ShareLink launched from a SwiftUI `confirmationDialog`/ActionSheet does not work. (developer.apple.com; SO 75109689; SO 60952334 + 4SwiftUI `Integrate_NSSharingServicePicker`)
- **Version / availability caveats.** `suggestedFileName` is iOS 17+; `NSSharingServicePicker` is macOS 10.8+; preview popover macOS 13+; collaboration-mode restrictions (`NSSharingCollaborationMode`, `CollaborationModeRestriction`, `sharingServicePickerCollaborationModeRestrictions`) macOS 15.0+/iOS 18+. Known "Save to Files" bug (FB11766691): blank sheet / `NSPOSIXErrorDomain Code=22`; workarounds are Info.plist keys `LSSupportsOpeningDocumentsInPlace`/`UIFileSharingEnabled` or preferring `DataRepresentation` + `suggestedFileName`. (developer.apple.com; forums thread 767476)
- **No share-sheet call sites exist in this repo** (`rg` share/sheet matches nothing but unrelated strings). The in-repo grep is the cheap ground-truth cross-check.

- **CheckStitchUITests/CheckStitchUITests.swift** (:18) — single XCTest smoke touches only `createChecklistButton`; **no export coverage in the UI suite**.

## Cross-Cutting Observations
- The export document is an in-memory `FileDocument` (JSON bytes); every platform panel (`fileExporter`, `fileImporter`, likely `ShareLink`) is anchored to the **root view** because sheet-nested presentation fails on macOS — a strong precedent for where any share-sheet entry point must live.
- A macOS `Startup`-style async presentation with `Task.sleep(for: .milliseconds(400))` after sheet dismissal is the established pattern for any root-owned modal that must appear after a sheet closes.
- The app target is a single source set compiled for iOS + macOS via `#if os(...)`; the FileDocument/share surface inherits this — platform differences must be inside `#if os(...)` in shared files.
- Core (`CheckStitchCore`) never touches platform UI; the `FileDocument`/URL/share plumbing lives entirely in the app target (`CheckStitch/`).
