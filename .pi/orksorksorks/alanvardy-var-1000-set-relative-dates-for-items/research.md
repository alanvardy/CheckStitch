# Research Findings

## Q1: How does the ChecklistItem Codable encoding work, and how does the versioned ChecklistCodec handle old, current, and unknown envelope versions?

### Findings
- The generic Codable/CodingKey mechanism is **not vendored in this repo** — `CustomCodingKey` has zero occurrences; every hit is a usage. The only other consumer besides the checklist model is `CheckStitch/BackgroundImageStore.swift:32,40`. Sample usage: `CheckStitchCore/Sources/CheckStitchCore/Checklist.swift:8` (`struct ChecklistItem: … Codable`), `:27` (`private enum CodingKeys: String, CodingKey { case id, title, modifiedAt, revision }`), `:30` (decoder `container(keyedBy: CodingKeys.self)`), `:38` (encoder container).
- Decode is **lenient, all fields via `decodeIfPresent … ?? default` except the identity keys**: `Checklist.swift:29-35` — `id`/`title` decode as required (absence throws); `modifiedAt` via `decodeIfPresent(Date.self, forKey: .modifiedAt) ?? .distantPast` (`:33-34`); `revision` via `decodeIfPresent(Int.self, forKey: .revision) ?? 0`. Header comment `:4-6`: the two optional fields are optional "so v1 payloads (which carried no sync state) still load."
- Same pattern up the stack: `Checklist` decode `:69-76` (`items ?? []`, `modifiedAt ?? .distantPast`, `revision ?? 0`); `ChecklistEnvelope` decode `:144-148` with comment `:141` "v1 payloads have neither deviceID nor tombstones" (`deviceID ?? ""`, `checklists ?? []`, `tombstones ?? []`); `version` is required via plain `decode` (`:145`). **Encode always writes all keys** (Checklist.swift:38-41, 79-82, 152-155) — there is no conditional-skip encoding.
- `ChecklistCodec` (`Checklist.swift:169-221`): `currentVersion = 2` (`:169`). `classify` (`:193-208`) first decodes only a `VersionProbe { version }` (`:222`), then: `case currentVersion` (2) → `.loaded(try JSONDecoder().decode(ChecklistEnvelope.self, …))` (`:198-199`); `case 1` → full decode → `.migratable(from: 1, checklists: legacy.checklists)` (`:200-203`); `default` → logs "Unsupported checklist payload version …; treating as empty", `.unsupportedVersion` (`:204`); any throw → `.unreadable` (`:205-207`). `Outcome` enum `:173-187`: `loaded(envelope) / migratable(from, checklists) / unsupportedVersion / unreadable`. Convenience `decode(data)` `:211-218` maps loaded/migratable → checklists, otherwise `[]`. Wire format: `encode` = `JSONEncoder().encode(envelope)` (`:220-221`).
- **v1→v2 migration precedent**: `Checklist.migrated(at date:)` (`Checklist.swift:89-104`) stamps `modifiedAt = date` and `revision = max(revision, 1)` on the checklist and every item — "v1 carried no sync state, so stamp it rather than rejecting the payload." Store init migrates in memory (`ChecklistStore.swift:69` `.migratable:` map over `$0.migrated(at: now())`) and sets `canOverwriteStoredPayload = true // never stall migration`. Remote side (`ChecklistSyncService.swift:129-130`) rebuilds migrated checklists into `ChecklistEnvelope(deviceID: "", …)` with `migrated(at: .distantPast)`. The store only ever encodes a current-version envelope (`ChecklistStore.swift:86`).
- `canOverwriteStoredPayload` (`ChecklistStore.swift:31`, doc `:29-30`: false only when the stored payload came from a newer app version — mutations still work in memory, saving is refused so that payload survives). Set **only** in `init` from `defaults.data(forKey: key)`, `key = "checklists.v1"` (:37): `.loaded` → true (:66), `.migratable` → true (:69), `.unsupportedVersion` → false (:72), `.unreadable` → true (:75), no stored data → true (:79). Gates: `canAcceptRemoteChanges` (:94); `apply(remote:)` guard `:225`; `save()` — the only KVS writer — refuses with `logger.error("Refusing to overwrite checklist payload written by a newer app version")` (`:271-274`). Sync interplay (`ChecklistSyncService.swift:126-133`): remote `.unsupportedVersion`/`.unreadable` → `.failed("Stored sync data could not be read.")`, local state preserved, nothing written over remote.

## Q2: What is the complete path of an item edit and of a remote payload?

### Findings
- **UI → store**: `CheckStitch/ChecklistDetailView.swift:152` `titleBinding(checklistID:, itemID:) -> Binding<String>` — `get` re-queries `store.checklist(id: checklistID)?.items.first {…}?.title ?? ""`; `set` forwards raw text into `store.updateItem(...)` per keystroke (body quoted in Q3).
- **Local mutation**: `CheckStitch/ChecklistStore.swift:190` `updateItem` — no-ops unless both indexes found; sets `title`, `revision += 1`, `modifiedAt = now()`, then `scheduleSave()` (:252). `scheduleSave` (:252): with `textEditDelay` (default `.milliseconds(300)`, `:46`) cancels the pending `Task` and sleeps, then `save()`; `nil` delay saves synchronously. `flushPendingSave` (:252 region, called from the view's `.onDisappear`) saves immediately.
- **KVS write**: `save()` (`ChecklistStore.swift:266`) — cancels pending, guards `canOverwriteStoredPayload` (:271), then `defaults.set(try ChecklistCodec.encode(envelope), forKey: key)` with `key = "checklists.v1"` (:44); fires `onChange?()` unless `isApplyingRemote`. `envelope` property (:82-86) is the only encoder: `ChecklistEnvelope(version: ChecklistCodec.currentVersion, deviceID:, checklists:, tombstones:)`.
- **Push**: `CheckStitch/ChecklistSyncService.swift:45-49` `start` wires `store.onChange = { schedulePush() }` and observes KVS external changes → `reconcile`. `schedulePush` (:120-129) debounces `pushDelay` default `.milliseconds(500)` (:33) then `pushNow()` (:104-109, synchronous). `reconcile` (:60-70) coalesces concurrent reconciles onto one `inFlight` task.
- **Remote write**: `CheckStitchCore/Sources/CheckStitchCore/ChecklistSyncing.swift:9-16` protocol is `Data`-only; `UbiquitousChecklistSync` (:22-23) with `write` = `store.set(data, forKey: key)` (:32), observer on `NSUbiquitousKeyValueStore.didChangeExternallyNotification` (:36-49). Same key `checklists.v1` in the mirroring cloud KVS.
- **Reconcile/apply**: `reconcileNow` (`ChecklistSyncService.swift:132-172`) — guards `store.canAcceptRemoteChanges`; reads remote; if cloud empty and local non-empty, seeds (`sync.write(encode(local))`, :154); classifies remote `.loaded` (as-is) / `.migratable` v1 (rebuilt, migrated at `.distantPast`) / `.unsupportedVersion`/`.unreadable` → `.failed`, never discards local. Then `store.apply(remote:)` (`ChecklistStore.swift:221-238`): guards `canOverwriteStoredPayload` (:225) and `remote.version == currentVersion` (:228); `ChecklistMerge.merge`; idempotence guard `merged != envelope`; sets `isApplyingRemote`, assigns `checklists`/`tombstones`, `save()`, restores flag; returns `visibleChanged`.
- **LWW merge** (`CheckStitch/ChecklistMerge.swift`): `wins` (:126-133 / :134-140 in sibling reads) = higher `revision`; tie → newer `date` (`modifiedAt`, `deletedAt` for tombstones); tie → lexicographically smaller `deviceID`. Symmetric. `mergedChecklists` (:81-102): the whole winning checklist provides name/revision/modifiedAt; `mergedItems` (:104-122): **whole-item replacement** — winner supplies title, revision, modifiedAt, nothing merges field-by-field. `mergedTombstones` (:59-79): union by `(checklistID, itemID)`, deterministically ordered; `:30-42` tombstones always suppress live entries (`itemID == nil` tombstones remove whole checklists).
- **Watch decoder**: `CheckStitchCore/Sources/CheckStitchCore/ChecklistSync.swift:13-51` `ChecklistSyncMessage` = `.context(Data)` (key `"checklists"`), `.runChecklist(UUID)`, `.requestChecklists`; `init?` `:33-46`. `WatchChecklistStore.receive` (:119-133): `.context(data)` → `if case .loaded(let envelope) = ChecklistCodec.classify(data) { checklists = envelope.checklists }` — **malformed or future-version payloads leave the previous list intact**. `.runChecklist`/`.requestChecklists` are phone-only (`break`). `start` (:88-94): `onMessage = receive`, `onActivated = requestRefresh`, `activate()`.
- **Unknown/malformed behavior summary**: missing envelope fields → defaults (Q1); version ≠ 1/2 → `.unsupportedVersion` (local: read-only lock; remote: failed, no write); decode throw → `.unreadable` (local: start empty, writable; remote: failed, no write).

## Q3: How does ChecklistDetailView render and edit one row per checklist item?

### Findings
- `CheckStitch/ChecklistDetailView.swift:9-10` — `struct ChecklistDetailView: View` keyed by `let checklistID: UUID` (not a parent `@Binding`); mutations go through `ChecklistStore` (comment :6-8). Body gates on existence (`:21`); else renders `ContentUnavailableView("Checklist not found", …)` (:127-129).
- **One `TextField` per item** inside `Section("Items")` (`:36-43`): `ForEach(checklist.items) { item in TextField("Item", text: titleBinding(checklistID: checklistID, itemID: item.id)) }` (`:38`) with `.onDelete { offsets in store.removeItems(from: checklistID, at: offsets) }` (`:41`). Item rows carry **no** accessibility identifier today (the name field and buttons do).

## Cross-Cutting Observations
- **Encoder writes everything, decoder forgives everything**: every type encodes all keys with no conditional skips (Checklist.swift:38-41, 79-82, 152-155), and decodes optional fields via `decodeIfPresent ?? default` (Checklist.swift:33-34, 73-75, 144-148). A new optional per-item field added to the struct's CodingKeys + decode/encode would already round-trip through the JSON wire format without the envelope codec changing; the open question areas are version semantics (below), not mechanism.
- **Versioning precedent is strict and two-sided**: `currentVersion = 2` (Checklist.swift:169); readers accept exactly `currentVersion` or the single supported legacy `1` (→ `.migratable`), anything else is `.unsupportedVersion` — which on the **local store** locks writes (`canOverwriteStoredPayload = false`, ChecklistStore.swift:72, 271) and on the **remote side** fails the reconcile without touching anything (ChecklistSyncService.swift:126-133). The watch decoder only accepts `.loaded` and otherwise keeps its prior list (ChecklistSync.swift:119-133). v1→v2 was handled without per-field migration code: missing-state fields default on decode, and `migrated(at:)` stamps sync identity (revision ≥ 1, modifiedAt) on the way in (Checklist.swift:89-104).
- **Item merge is whole-item LWW, not field-level**: winners are decided by `revision > modifiedAt > deviceID` (ChecklistMerge.swift:126-133) and the winning item replaces the loser entirely (mergedItems :104-122) — any new field lives or dies with the item revision as a unit. Tombstones are never garbage-collected (ChecklistStore.swift:17-19 area; ChecklistMerge.swift:59-79).
- **Two reminder paths with opposite store lifetimes**: the live path builds a fresh `EKEventStore()` per call (ChecklistReminders.swift:9), while both the core mirror doc (ReminderCreating.swift:10-12) and the phone adapter comment (PhoneSyncAdapter.swift:9) mandate one long-lived store because `EKReminder` holds a weak store reference. Both paths set only `title` + `calendar`; the title-only seam signature is `create(title: String)` (ReminderCreating.swift:9) vs the live path's `create(from checklist: Checklist)` (ChecklistReminders.swift:8).
- **The reminder-creation seam exists but is dormant**: `ReminderCreating`/`AppEnvironment`/`EventKitReminderCreator`/`ChecklistCreator`/`ChecklistViewModel` are wired only in tests via `SpyReminderCreator`; the shipping app calls `ChecklistReminders.create` directly (ContentView.swift:312, MyApp.swift:67).
- **UI conventions**: item rows are unbuffered per-keystroke bindings through the store (ChecklistDetailView.swift:152); the checklist name is the only buffered/draft edit (:33-34, 82-89); a11y ids are camelCase `<verb><noun>Button` / `<noun>Field` / confirm-cancel pairs, and item rows currently have none.
- **View testing is value-description based**: SwiftUI scene staging is impossible headless, so `ChecklistDetailViewTests` asserts on `String(describing: …)` and leaves interaction to store tests (ChecklistDetailViewTests.swift:9-15, 39-43).

## Open Areas
- The SWIFT SDK definitions of `Codable`/`CodingKey`/`decodeIfPresent` are not vendored in-repo (Q1 child budget: not findable).
- No v2→v3 (or "add-field-bump") version transition exists yet — only v1→v2 has precedent, and `currentVersion` is a single constant consulted in one place (Checklist.swift:169, 198).
- The external `import EventKit` module's full `EKReminder` surface beyond `title`/`calendar`/(`dueDateComponents`, from SingleThread) is unreferenced in this repo.
- `ChecklistSyncCoordinator.swift` internals (watch `runChecklist` → reminder creation) and the watch UI (titles only) were not deeply followed in this phase.
